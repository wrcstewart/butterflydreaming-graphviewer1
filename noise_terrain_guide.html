1. The one idea

There is no stored map. Height is a function.

height01(xKm, zKm)  →  height

  xKm, zKm   where in the world, in KILOMETRES from an arbitrary origin.
             Any real values. There is no range and no edge.
  returns    one number in [0, 1]. A NORMALISED height, not metres — §2.6
             turns it into an altitude.
  seed       NOT a parameter. It is bound when the terrain object is made,
             so one terrain object is one world.

It is a pure function of world position and seed: the same coordinates always return the same height, with nothing remembered between calls. Everything the page can do follows from that single property:

  • The world has no edge. Chunk (0,0) and chunk (10000, −7000) are the same amount of work. Walking away and back returns the identical ground, asserted by the self-test.
  • Chunks need no stitching. Two patches generated independently agree exactly where they meet, because both evaluate the same function at the same coordinates. The readout measures this at max difference 0, not "within a tolerance".
  • Detail can be added without moving anything. More octaves is more detail at the same place — which is a working level-of-detail path (§7).

The cost is that the function must be evaluated for every vertex drawn, every time. That is why the page is quick at 2×2 chunks and deliberate about going larger.

2. How the scene is constructed

Six steps, in order.

2.1 Chunks, generated independently

chunk(cx, cz, { chunkKm, res })  →  Float32Array

  cx, cz     WHICH chunk, as integer chunk coordinates — not kilometres.
             Chunk (3, −2) starts at world (3·chunkKm, −2·chunkKm).
  chunkKm    the width of one chunk, in km
  res        cells per side
  returns    (res+1)² heights in [0, 1], row-major, index j·(res+1)+i.
             The extra row and column are the edge SHARED with the next
             chunk, so adjacent chunks each hold a copy of it.

The page asks the terrain for k × k chunks and assembles them. The default 2×2 of 4 km at 64 cells is 8 km of ground in 16,900 samples.

Each chunk comes from its own chunk(cx, cz) call. That is deliberate: it is the method's central claim under test, so the page gets its geometry the same way a real streaming world would, rather than slicing up one big grid afterwards and proving nothing.

2.2 The edge test

Before drawing, every pair of adjacent chunks is compared along its shared boundary — k=2 gives 4 pairs, k=3 gives 12. The result appears on the shared edges line. It reads exactly 0 with every control engaged.

At k=1 there are no adjacent pairs, so the line says not tested rather than reporting a pass from a test that never ran.

2.3 One mesh per chunk

Each chunk becomes its own THREE.PlaneGeometry, placed so the set tiles a frame 2 units wide. Separate meshes, again deliberately: if the heights disagreed, a crack would open where they meet, and a single stitched surface would hide it.

2.4 Normals from an apron, not from the mesh

This is the one part that cannot be done per-chunk. three.js's computeVertexNormals() takes no arguments and rewrites a geometry's normal attribute in place, averaging only the triangles of its own geometry — which is the whole problem. A vertex on a tile boundary takes its normal from one side only, while its twin in the next tile takes a different one from the other side. The heights match perfectly and the shading still creases — it showed as two stitch lines dividing the scene into four.

So each chunk also carries a one-cell apron: the heights just outside its own edges. Normals come from the height gradient across that apron, so both tiles compute the same normal at a shared vertex — verified bit-identical. This is only possible because height01 is defined everywhere, which is the same property the whole method rests on.

2.5 Colour in a vertex attribute

The surface colour lives in a per-vertex attribute and the material stays white, because three.js multiplies material colour by vertex colour. Changing scheme refills the attribute and does not rebuild the field.

Why the alpine colours are lit dimly: clipping.

Two terms first.

  • Channel. A screen colour is three numbers — red, green, blue — each from 0 (none) to 255 (full). Each of the three is a channel. The brown used here is 139, 90, 43: a fair amount of red, less green, little blue. Inside the renderer the same channels run from 0.0 to 1.0 instead of 0 to 255; it is the same scale, divided by 255.
  • Clipping. A channel cannot go above full. If a calculation asks for red at 1.4, the screen shows 1.0. The excess is not stored anywhere — it is simply lost. (The code comments call this pinning. It has nothing to do with the stable zoom checkbox, whose id happens to be pin.)

The renderer works out how bright each point is like this:

shown colour  =  surface colour  ×  light

  surface colour   the scheme's colour for that point — e.g. brown 139, 90, 43.
  light            sun × (how squarely the slope faces the sun, 0 to 1)
                   + hemi.
  sun, hemi        the two lights' strengths, set per scheme. sun is the
                   directional light; hemi is the even sky-and-ground light
                   that reaches every slope, so shadowed sides are not black.
  returns          one value per channel, CLIPPED at full (1.0, i.e. 255).

The brightest any point can be lit is a slope facing the sun squarely, where light = sun + hemi. Call that the gain. Everything comes down to it:

  • Gain at or below about 1.15: colours survive. Each channel is multiplied by the same amount and none goes far over full, so the ratios between red, green and blue stay put — and the ratios are what make a colour brown rather than cream.
  • Gain well above that: colours break. The alpine scheme once ran sun 2.0 with hemi 0.55, a gain of 2.55. Brown 139, 90, 43 × 2.55 asks for about 354, 229, 110. Red clips at 255 and green nearly does, so the sunlit side shows 255, 229, 110 — a pale cream. The red-to-green ratio that made it brown, 1.55, has collapsed to 1.11. Green suffered the same way and showed as near-white.

So the alpine scheme now runs sun 0.75, hemi 0.40 — a gain of 1.15 — the most that keeps all three of its colours clean. Its sunlit brown is 164, 106, 51, still brown. That is why it looks dimmer and flatter-lit than the other schemes: in the one scheme where colour carries information (green = below the tree line, brown = above it, white = above the snow line), exposure is set to keep the colours true, not for contrast.

2.6 The scales in play

Four different scales meet in the scene. Most confusion about the page comes from mixing them, so here they are separately:

scaleunitwhat sets it
ground — across the landkilometreschunk size × chunks across = the width of land in view
field height — what height01 returnsnone: a number in [0, 1]the noise itself; it has no unit until one is chosen
real height — relief and altitudemetresmountain height, through one fixed constant (below)
screen — what three.js drawsframe unitsderived from the other three, so the picture is true to scale

Turning the unitless height into metres. height01 gives a number between 0 and 1 with no unit, so something has to say how many metres one unit is. The page fixes this once, for every setting:

one unit of field height  =  10,000 m      × mountain height

  mountain height   the slider, 0.01 to 1 (default 0.45). So at the default,
                    one unit of field height is 4,500 m.

From that, the two figures the readout reports:

relief    (hi − lo) × mountain height × 10,000      metres

  hi, lo      the highest and lowest field heights in view, each in [0, 1].
  returns     the height from valley bottom to top peak in METRES.
              Note that chunk size does not appear: widening the view
              does not change how tall the mountains are.
  example     heights spanning 0.47, at mountain height 0.45:
              0.47 × 0.45 × 10,000 = 2,115 m.

altitude  valley floor + (h − lo) × mountain height × 10,000      metres

  h           the field height at the point, in [0, 1].
  valley floor   the control: the altitude of the LOWEST point in view,
              default 1,000 m. It is a datum, so everything is measured
              up from it.
  returns     the point's height above sea level in METRES — the number
              the tree line and snow line are compared against.

Why it is done this way. Because the metre scale is fixed and does not depend on the ground width, the two kinds of control do separate, physical things:

  • mountain height changes how tall the mountains are — in metres, and on screen.
  • chunk size and chunks across change how much land is in view. Taking in more land makes the same mountains look flatter, which is what happens when you look at a wider landscape.

The screen scale is then derived so that one metre up is drawn the same length as one metre across. There is no vertical exaggeration: a slope is drawn at its real steepness, so steep-looking ground really is steep (the camera's perspective still foreshortens what you see, as it would looking at real hills). (An earlier version derived metres from the ground width, so widening the view scaled both directions together and the picture never changed — the control could only relabel the axis.)

3. How the noise is generated

height01 runs the following in this order. Each stage is a control, so this is also the map of what affects what.

  (x, z) in km
      │
  1.  warp ............ displace the sample point by a second, slower noise field
      │
  2.  stretch ......... divide x and z unequally  (area-preserving)
      │
  3.  octave sum ...... the mountains: 7 rotated simplex samples at doubling
      │                 frequency and 2^−H amplitude, each weighted by w
      │
  4.  ÷ norm .......... normalise to roughly [−1, 1]
      │
  5.  slow layer ...... a 2-octave swell, sampled at the UNWARPED position
      │
  6.  combine ......... baseShare·swell + (1−baseShare)·beltMask(swell)·mountains
      │
  7.  squash .......... hard clamp, or a soft knee, into [0, 1]
      ▼
  height in [0, 1]

3.1 The octave sum — the mountains

sum = Σ  aₒ · wₒ · simplex( rotateₒ(x/su, z/sv) · fₒ + offsetₒ )
       o
      fₒ = (1/widest) · 2ᵒ          amplitude  aₒ = (2^−H)ᵒ

where simplex(u, v) → a number in about [−1, 1] is one sample of the seeded 2D simplex lattice, rotateₒ turns the sample point by 0.83·o radians, and offsetₒ shifts it by (17.3o, −9.1o). wₒ is the hetero weight, 1 unless that control is on.

  • f₀ = 1/widest, with coordinates in kilometres. So the lowest octave's wavelength is the widest feature, and the finest detail is widest / 2^(octaves−1). What governs the look is the ratio of widest to the ground in view: 4 km features across 8 km of ground gives two big features per side.
  • Each octave is rotated by 0.83 radians and offset by (17.3o, −9.1o). Simplex noise has a lattice, and both the rotation and the offsets exist to stop the octaves lining up on it. The readout's anisotropy figure is the check that this worked; it reads about 0.9, i.e. no detectable direction.
  • gain = 2^−H is what makes the sum fractional Brownian motion. Note the H asked for is not the H delivered — see §6.
  • norm = Σ gainᵒ, so the sum lands in roughly [−1, 1] whatever the octave count. With stable zoom on, that divisor is computed over a fixed budget instead, which is what makes adding octaves leave the coarse shape exactly where it was.

3.2 The four modifiers

Plain octave noise is statistically homogeneous — the same everywhere — so every patch is equally rough and nothing distinguishes a plain from a range. These break that, and they break different things:

what it breakshow
warpuniformity of placementthe sample point is displaced by a slower noise field before the octaves are summed, so ridges become sinuous and peaks stop being evenly scattered
stretchisotropyx and z are scaled unequally, elongating every feature along one axis. Area-preserving — √r one way, 1/√r the other — because stretching one axis alone just lowers the frequency along it and smooths the whole surface
heterouniformity of roughnesseach octave's weight w is modulated by the accumulated elevation so far, so detail appears where the ground is already high and dies in the lows: rough peaks over smooth plains
the slow layerthe scaleadds a swell much larger than any mountain, which also decides where mountains grow at all

hetero's weight is normalised to average exactly 1 (w = (1−h+h·elev)/(1−h/2)), so it redistributes detail rather than removing it. Without that divisor the mean weight is 1−h/2 and the control simply smoothed the terrain.

All the figures quoted for these three are measured against plain noise with the slow layer OFF, and that matters, because the belt overlaps with hetero. The honest comparison is the correlation between a patch's roughness and its height — which is what "rough peaks over smooth plains" actually means:

roughness-to-height correlation
plain noise0.008 — none at all, every patch equally rough
hetero 1, no belt0.439
the belt, hetero 00.793
the belt and hetero 10.831

The belt is much the stronger mechanism, because mountains only grow on the swell's high ground, which ties roughness to height by construction. So at the page's defaults hetero adds little — reach for it when you want rough peaks without confining the mountains to a belt, which is a different landscape: mountains everywhere, but only the high ones rugged.

3.2a Which mechanism to reach for

They are not interchangeable, and two of them cost something:

  • Want large-scale organisation — ranges here, plains there? The slow layer. Nothing else supplies structure bigger than one mountain.
  • Want lineation, ridge-and-valley country? Stretch. It is the only one that produces a direction, and it costs roughness (3.55 → 2.33 at 3:1) because a stretched axis has gentler gradients.
  • Want irregular placement, sinuous ridges, uneven spacing? Warp. It costs the grain if you also want stretch.
  • Want rough summits over smooth ground, with no belt? Hetero. Free of side effects — it keeps isotropy and does not reduce roughness.

3.3 The slow layer, and why it is one field doing two jobs

height = baseShare·swell  +  (1 − baseShare)·beltMask(swell)·mountains
slowAt(xKm, zKm)  →  a number in about [−1, 1]

  xKm, zKm   the UNWARPED, UNSTRETCHED world position, so the regional shape
             is not dragged about by controls meant for the mountains
  returns    the regional swell: two octaves of its own lattice at
             wavelengths baseKm and baseKm/2, normalised

The swell has its own noise lattice, independent of the mountains'.

It is used twice: as the gentle rolling ground and as the mask deciding where mountains grow. So ranges stand on the high ground of the swell, its flanks carry low-amplitude mountains — which is what a foothill is — and it keeps rolling across the lows where no mountains grow at all. That also gets the geology right for nothing: real ranges sit on uplifted ground rather than scattered at random.

beltMask(swell01)  →  a factor in [0, 1]

  swell01    the slow layer's value mapped to [0, 1] — how high this ground
             stands on the regional swell
  returns    the share of the mountain amplitude that survives here:
             1 well inside the belt, 0 well outside, smoothstepped between

It is u = (swell01 − (1−coverage))/foothills + 0.5, clamped to [0, 1], then u²(3−2u). Smoothstep because it is flat at both ends, so the belt has no crease at its edge.

3.4 The squash

squash(v)  →  a number in [0, 1]

  v          the combined height, near [0, 1] but free to overshoot either rail
  returns    v clamped hard, or eased through a knee if SOFT CEILING is on

0.5 + 0.85·combined is finally passed through it. The original method uses a hard clamp, and where a broad swell overshoots it the whole top is sheared off into a dead-flat mesa — measured, 5.3% of the grid as a single region in one corner at widest 16 km over 3 octaves. Soft ceiling replaces the corner with a knee over the outer 12%, approaching the rail asymptotically and never reaching zero gradient, so a swell stays curved however far it overshoots.

6. Things that look like faults and are not

  • The H asked for is not the H delivered. 0.50 gives 0.47, but 0.90 gives only 0.72. Discrete octave spacing and simplex's own spectral shape are not a true power law. This is the method's behaviour, and the readout shows both figures rather than implying they agree.
  • Relief is always exactly 1.000 with the layer off. height01 clamps to [0, 1], so the method normalises itself and relief is not a measure here. That is why metres come from the height control alone.
  • The anisotropy figure is noisy, ±0.4 on one reading at this grid size, because a red spectrum puts nearly all its power where the grid has fewest samples per direction.
  • Gentle ground outside a belt is the design, not the clamp. The readout distinguishes them.
  • Stretch costs some roughness. A stretched axis has gentler gradients; even area-preserving, roughness falls from 3.55 to 2.33 at 3:1. Unavoidable.

7. The zoom ceiling, and the LOD path

Zooming in past the finest octave shows nothing new. The octave set is fixed, so detail stops at widest / 2^(octaves−1) — 62.5 m at the defaults. Sampling one 200 m patch from 28.6 m spacing down to 0.8 m gives relief 0.1975, 0.1976, 0.1975: a smoother interpolation of the same surface, no new ground. Raising cells per chunk does not help; raising octaves does.

That is also the level-of-detail path, and it works because height01 is a pure function: adding octaves while zooming leaves the coarse shape within half a percent, and exactly with stable zoom on. Far chunks few octaves, near chunks many, and the mountain does not move. Nothing in the page consumes this yet — a walk-through would.

Appendix A. Light, layers and blend modes — terms explained

This appendix is about where the terrain is going rather than how it is built: an aesthetic, possibly VR, scene with drifting mist and a moving sun and moon, often shown at low opacity as one layer of a collage. It collects the terms that discussion needs, each defined before it is used. Throughout, a colour channel runs from 0 (black) to 1 (white) — the same scale as 0 to 255, divided by 255 (§2.5 defines channel and clipping).

A.1 Fitting light to the screen

§2.5 describes capping the light so no colour clips. That works when every light source is known in advance. With mist that thickens and thins and a sun that moves, the worst case cannot be known in advance, so a cap calculated ahead is either broken when the mist thickens or so cautious the scene is always dim. The only place the total light is known is at the end, pixel by pixel. So the recommended order is:

Step 1 — add up all the light with no ceiling, in linear values (A.4). Sun, moon, sky and mist all contribute freely; nothing clips yet.

Step 2 — exposure as an artistic control. Dusk should feel like dusk and night should be dark, so exposure is set by hand. If it adapts at all, slowly and partially — in VR a sudden brightness change is uncomfortable.

Step 3 — a soft shoulder on each pixel's largest channel (A.4). If a pixel's largest channel would pass 1, all three channels are scaled down together, so the colour keeps its hue and only the brightest pixels are affected:

m = max(r, g, b)
if m > 1:  (r, g, b) = (r, g, b) / m          the hard version

  r, g, b   one pixel's channels in linear values, with no upper limit.
  returns   the same pixel with its largest channel at most 1, and the
            ratios between r, g and b unchanged — so the same hue.

The soft version starts compressing a little below 1 instead of cutting off at it, so bright mist rolls off into haze rather than flat white.

Step 4 — a colour grade, if wanted: cooler for moonlight, warmer at dusk.

Clipping becomes a deliberate effect in small doses — a sun glint allowed to bloom. What to avoid is large flat areas, blown out or crushed (A.4), because they carry no texture, and in a collage that matters more (A.3).

A.2 Blend modes

Blend mode. When one image is laid over another, a blend mode is the rule for combining each pixel of the top image with the pixel directly beneath it. The ordinary rule, normal, is that the top covers the bottom; with lowered opacity, the bottom shows through in proportion. Other blend modes do arithmetic on the two pixels instead. Each rule is applied to red, green and blue separately.

Multiply.

result = top × bottom

  top, bottom   the two pixels' values for one channel, each in [0, 1].
  returns       their product, in [0, 1]. Never lighter than either input.
  • White on top (1) leaves the bottom unchanged — × 1 changes nothing.
  • Black on top (0) gives black — × 0 is 0.
  • Anything between darkens. Like two slides stacked on a light box: each can only block light.

Bottom at mid-grey 0.5: top 0.8 gives 0.4, top 1 gives 0.5, top 0 gives 0.

Screen.

result = 1 − (1 − top) × (1 − bottom)

  top, bottom   as above, each in [0, 1].
  returns       a value in [0, 1]. Never darker than either input.

The mirror image of multiply:

  • Black on top (0) leaves the bottom unchanged.
  • White on top (1) gives white.
  • Anything between lightens. Like two projectors shining on one screen: each can only add light.

Bottom at 0.5: top 0.8 gives 0.9, top 0 gives 0.5, top 1 gives 1.

A rough guide to choosing: multiply for what should darken or shade — terrain relief, texture, ink. Screen for what should glow or lighten — mist, light, the moon. Normal at low opacity for a gentle mix.

A.3 Why flat extremes spoil a collage

At low opacity most of a layer's colour is diluted away, and what carries through is its variation in brightness. A flat region is a flat veil. The two blend modes make it sharper still:

blend modewhere the terrain is blown out to white (1)where it is crushed to black (0)
multiply× 1, so the image below shows unchanged — the terrain vanishes there, a hole× 0, so the result is black — the image below is blotted out
screenthe result is white — the image below is burnt out to a white patchthe image below shows unchanged — the terrain vanishes there

Either way, one extreme leaves a hole and the other a solid patch, and the terrain's own detail is gone in both. A terrain whose values spread through the middle range has something to contribute everywhere — which is what the soft shoulder in A.1 produces.

A.5 Three or more layers

Blend modes apply to any number of layers. Layers are stacked bottom to top, and each layer has its own blend mode and its own opacity. A layer's mode does not combine it with one particular other layer: it combines it with the result of everything below it. The work goes upward:

running = layer 1          the bottom: nothing is below it, so its mode is ignored
running = blend(layer 2 onto running, by layer 2's mode and opacity)
running = blend(layer 3 onto running, by layer 3's mode and opacity)
  …
final   = running

One pixel, worked through:

layervalueits moderesult so far
1, bottom — a photo0.6—0.6
2 — the terrain0.5multiply0.6 × 0.5 = 0.30
3, top — mist0.4screen1 − (1 − 0.4) × (1 − 0.30) = 0.58

The terrain darkened the photo; the mist then lightened the result.

Order matters — except within one mode.

  • All multiply, or all screen: order makes no difference. Three multiply layers give a × b × c in any order, as slides on a light box block the same light however they are stacked.
  • Mixed modes: order changes the result. Swap the top two layers above — mist multiplied first, terrain screened on top — and the pixel is 0.62, not 0.58.
  • Opacity is applied as each layer goes on: a layer at 30% gives 30% of its blended result and keeps 70% of what was below.

How the mode is chosen. It is set per layer, by whoever builds the picture; nothing chooses it automatically.

wherehow each layer's mode is set

inside a 3D scene (three.js)each material's blending setting; multiply is built in, screen needs a short custom rule

In BD, as of 2026-11-11: the collage uses no blend modes — every layer is drawn normal. Adding them is one per-layer setting, most simply a mix-blend-mode on each layer's frame. The question to settle first is who chooses it: the person assembling the collage, through a control, or the module's script.
