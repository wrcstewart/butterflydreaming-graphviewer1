# Auto-backup on every DB-mutating bd_tool.js subcommand

User asked (2026-07-23) to "make it as safe as possible" against curator work being overwritten by later .md-driven writes. Answered by wiring pre-flight backups into every DB-mutating subcommand.

**Why:** User was mid-migration (Cluster→SubFamily re-parenting via the curator page), worried that running `bd_tool.js write` on `nav_nodes_text.md` for a small text edit could clobber their in-progress edge work. Diagnosis was: `write` only touches text properties (`SET n += $set` where the set only contains `text`), never edges — so no *actual* risk. But the perceived risk was enough to justify hardening the "just in case" case.

## The rule

Every subcommand that writes to Memgraph does a `preFlightBackup(tag, mdPath)` call before touching the DB. Skipped ONLY when:
- `--dry-run` is passed (no DB write happens anyway)
- `--no-backup` is passed (explicit opt-out)
- Nothing is actually flagged for update in the source .md (a `write` with all flags false is a genuine no-op — no need to snapshot)

Applies to: `write`, `sync-helpers`, `backfill-urls`, `apply-subfamily-labels`. Does NOT apply to `cypher` (intentional low-level tool — user owns their own safety there).

## What gets saved

Both artefacts land in `./backups/` at the repo root, alongside the manual `bd_tool.js backup` command's output:

- `memgraph_<tag>_<stamp>.cypher` — full `DUMP DATABASE` (roughly 800 KB, one Cypher statement per line, replayable with `cat file.cypher | mgconsole` after `DROP DATABASE`)
- `<source>.md.<tag>_<stamp>.bak` — byte-identical copy of the source .md **before** the flag reset that `write` does at the end

Filename `<tag>` = the subcommand name (`write`, `sync-helpers`, etc.), so a directory listing tells you which command produced each snapshot at a glance.

## Restore procedure

Documented in full in `BackupNotes.md` at the repo root. Quick version:
- To undo a bad `write`: `cp backups/<file>.write_<stamp>.bak <original>.md` to restore the .md, then re-run `write` (idempotent — text `SET n += {...}` just re-applies).
- To roll back the whole DB: stop server → `mgconsole` → `DROP DATABASE memgraph; CREATE DATABASE memgraph; USE DATABASE memgraph;` then `SOURCE '<path>/memgraph_<tag>_<stamp>.cypher';` (or paste the file's contents into mgconsole).

Whenever a change is pushed to a file that a user's browser might have cached
(standalone `wrcstewart.github.io/*` deployments, BD-served static files
without cache-bust query strings), pick a **visible entity** — usually the
most-prominent button — and paint it in a canary colour that ROTATES on every

**Why:** the user is often on iOS Safari or through the Cloudflare tunnel,
both of which cache aggressively. Without a canary they have no way to tell
whether a "not working" observation is a real bug or just an old cached
version being served. The rotation ensures each new push produces a
visibly-different UI, so a repeat colour = same version = cache issue.

**How to apply:**
- Every commit that touches a browser-cached file gets a canary tweak.
- Pick the next colour in the RGB rotation from wherever the last one left
  off (grep the file for the current canary colour to check).
- Use pure primary hex: `#FF0000` (red), `#00FF00` (green), `#0000FF` (blue).
- Add a comment noting "next = <colour>" so the sequence is visible in-file.
- User may occasionally override for a specific colour (e.g. "canary yellow
  this time"); after that, resume RGB rotation from the next primary.
- Remove the canary block entirely only when the user explicitly says
  "remove the canary" — otherwise it stays as a live-version indicator.

Related: [[bd-m-abc]] (established the canary pattern), [[fractal-music]]
(where the rotation rule was formalised).

## FILE: feedback_cy_fit_padding.md

```markdown
---
name: feedback-cy-fit-padding
description: "Use fitPadding(cy, maxPad) instead of a raw pixel literal as the second arg to cy.fit() — absolute padding crushes content on phone canvases"
metadata: 
  node_type: memory
  type: feedback
  originSessionId: df7b3b89-3294-4783-bab4-752a678ff4ef
---

**Always pass `fitPadding(cy, maxPad)` as the second argument to `cy.fit(...)` — never a raw pixel literal.** The cytoscape API takes absolute pixel padding, so the same `80` or `120` eats a far bigger fraction of a phone canvas than a desktop one.

**Why:** Concrete incident on 2026-06-24 (commit `57755ce`). The init `cy.fit(root, 120)` rendered the root at ~78% of canvas width on desktop (1000px wide) but only ~26% on iPhone (350px wide). Same call, same root node, different viewport — but absolute padding is "fair in pixels, unfair in viewport fractions". The smaller the canvas the more punishingly the padding eats your content. Subsequent early-expansion fits (`cy.fit(visible, 80)` etc.) had the same problem until the family view, by which time the bounding box of nodes was wide enough to dominate the padding.

**Helper signature:**
```js
function fitPadding(cy, maxPad) {
  const dim = Math.min(cy.width(), cy.height());
  return Math.max(20, Math.min(maxPad, dim * 0.08));
}
```

- `0.08` of the smaller canvas dim is the chosen sweet spot at this codebase's size range.
- `Math.max(20, ...)` floors so content doesn't glue to the canvas edge.
- `Math.min(maxPad, ...)` caps so desktop doesn't waste space — pass the original "ideal" padding value as `maxPad` and you'll get the old behaviour on large canvases.

**How to apply:**
- When adding a new `cy.fit(eles, N)` call site, write `cy.fit(eles, fitPadding(cy, N))` from the start.
- When editing an existing call site, convert the literal to the helper. Existing call sites at the time of this writing are all in `viewer.js` — search `cy.fit(` to enumerate.
- `fitPadding` lives at module scope in `viewer.js` (defined just above `setSystemText`). Don't shadow it inside `setupInteractions`.
- The tuning knob is the `0.08`. If a future device class makes content feel cramped or sparse, that's the one number to change.

**Doesn't apply to:** `cy.fit()` calls inside the cytoscape layout config (e.g. `layout: { fit: true }`); those go through cytoscape's internal padding which isn't a number we control.

See [[chat-panel-state]] for current viewer.js layout map.

**Always pin `#cy.style.top` to the bottom of the current panel BEFORE calling `cytoscape({ container: ... })` in `init()`.** Otherwise the initial `cy.fit(root, 120)` measures the canvas using the CSS fallback (`top: 158px`), and any later `cy.style.top = …` + `cy.resize()` preserves pan rather than re-fitting — so the root ends up off-centre.

With `#default-panel` at 17dvh the discrepancy between fallback and reality was small enough to look centred. After doubling `#default-panel` to 34dvh on iPhone, the root landed near the bottom of the visible canvas — same bug, bigger gap exposed it.

**How to apply:**
- The pin block lives just before the `const cy = cytoscape({...})` call in `init()`. Don't move it later "for ordering reasons" without re-adding a `cy.fit(root, ...)` after `cy.resize()`.
- On chat-panel toggle, `positionCyEl()` + `cy.resize()` + `cy.fit(undefined, 40)` runs in `requestAnimationFrame` from `toggleChatMode`. That path is correct because it re-fits explicitly.
- If you ever introduce a new vertical-space element above `#cy` (a new bar, taller panel, etc.), the init-time pin will still be correct because it reads `getBoundingClientRect().bottom` of `#default-panel` dynamically.

The rule above is about the size **at the moment focus lands** — Safari decides
whether to zoom then, not from the resting style. So a field can be denser than

#script-input:focus  { font-size: 16px; line-height: 1.45; }

right: it reads as the field opening up for editing.

**How to apply:**
- Reach for this when a field must be BOTH dense to read and typable. Otherwise
  the plain ≥16px rule still stands — this is an exception with a reason, not a
  new default.
- Bump `line-height` with the font or the text jumps position as well as size.
- Only worth it on a field users read more than they type.
- A `readonly` field never fires the zoom at all, so it can simply be small —

# Media-module control convention (established 2026-07-02)

User said explicitly: *"These rules will apply in general to media modules."* So this pattern is the default any time a new visual/audio/whatever module gets a control panel — not just V_Kolam.

## The rule

Every numeric-arg `%%bd_` directive gets a **+/− stepper** control, laid out as:

```
[−] [value] [+]        ← stepper row (buttons flank a centred value display)
   label               ← label immediately below, matching the directive name
```

- **`−` on the left, `+` on the right** (matches every quantity picker users have seen).
- **Value display** in the middle, monospace, showing the current numeric value.
- **Label** below the stepper, using the directive name verbatim after `%%bd_` (i.e. `step`, `angle_drift`, `colour_speed`, `saturation`). Not "Step" or "Colour Speed" — the underscored directive form. Rationale: keeps the UI and the script directive name in lockstep, so users editing the script know exactly which knob maps to which line.
- **Small vertical gap** (~6–10 px) between each button-label pair.
- **One stepper per field**, not a shared pair with a dropdown selector — fewer taps, no hidden "which field am I editing" state.

## Why steppers (not sliders, not native number inputs)

- **Native `<input type="number">` spin buttons don't render on any mobile browser** — iOS Safari, iOS Chrome, iOS Firefox (all WebKit-forced), Android Chrome, Android Firefox. Universal mobile convention. Text input is cumbersome and unreliable on iOS.
- **Sliders** communicate through position alone, which is problematic given [[user-colour-vision]] and general precision needs (0.375 vs 0.4). The stepper's text value stays readable.
- **Same UI on desktop and mobile.** No branching CSS.

## Panel layout

- **Desktop (landscape iframe):** single-column vertical stack, controls hug the left edge (`flex-direction: column; align-items: flex-start`).
- **Mobile portrait** (`@media (max-aspect-ratio: 1/1)`): row-wrap allowed, panel capped at `40vh` with `overflow-y: auto`, so all controls remain reachable without a giant scroll list.

## Excluded / hidden fields

- Directives with **compound structure** (like `angle` + `angle_minutes` + `angle_seconds` in V_Kolam) — expose only the top-level knob. The finer components stay in the DOM as `<input type="hidden">` so any automation (e.g. drift-tick propagation) still reads/writes them, but no UI clutter.
- **Derived / display-only** values (e.g. Kolam's old "×4.0" readout beside `colour_speed`) — dropped. Labels match directives; no extra multipliers or unit conversions in the UI.

## Wiring pattern (non-negotiable bits)

Keeps the existing render pipeline unchanged:

1. Underlying `<input type="number" class="stepper-source" min max step value>` is the source of truth. Hidden via `.stepper-source { display: none }`.
2. `stepControl(input, delta)` reads `min`/`max`/`step` off the input, computes the new value, clamps, snaps to the step grid, trims float noise (`parseFloat(next.toFixed(4))` — because `0.1 * 3 === 0.30000000000000004`), sets `input.value`, and dispatches a bubbling `input` event.
3. Existing `handleControlChange` (bound to each input's `input` event) fires unchanged, so no rewiring of the render / postMessage plumbing was needed.
4. `updateValueDisplays()` syncs every `.stepper-value` span from its target input via `data-target` — called after `setControlValues(directives)` on incoming script updates.

## iOS-specific hardening (learned the hard way, 2026-07-02)

On the `.step-btn` element these five CSS properties are all required — dropping any one causes a regression:

```css
touch-action: manipulation;                /* kill 300 ms tap delay + double-tap zoom */
user-select: none;
-webkit-user-select: none;                 /* older iOS Safari still needs the prefix */
-webkit-touch-callout: none;               /* suppress long-press callout / magnifier */
-webkit-tap-highlight-color: transparent;  /* no grey flash halo */
```

**Why:** without `-webkit-touch-callout: none`, holding the button for even a short moment on iOS triggers the text-selection cursor / magnifier callout, which then needs clearing by tapping elsewhere. iOS gives no way to lengthen the dwell time — the property outright suppresses the behaviour, which is what you want on a stepper button anyway.

**Apply the same triple** (`user-select: none; -webkit-user-select: none; -webkit-touch-callout: none;`) **to `.stepper-value` and `.control-row label`** as well — user reported (and confirmed the fix for) the same long-press callout on the value display AND on the label text. Anything with reachable text under a finger needs the triple. Skip `touch-action` and `-webkit-tap-highlight-color` on non-interactive elements — those are button-specific.

## Press-and-hold repeat

- **Tap** = single step.
- **Hold** = repeat at ~16 Hz (60 ms interval) after a **400 ms initial delay**. Necessary because saturation / lightness / any 0–100 range with `step: 1` would be tedious tap-tap-tap otherwise.
- Handlers use **pointer events** (`pointerdown` / `pointerup` / `pointercancel` / `pointerleave`) — unified touch+mouse. No `click` listener; `pointerdown` calls `preventDefault()` and captures the pointer so drag-off cancels cleanly.

## Related

- [[a42-visual-module]] — the V_Kolam implementation of this convention.
- [[user-colour-vision]] — the reason sliders were rejected.
- [[ios-input-zoom]] — separate iOS gotcha (font-size ≥16 px on focusable inputs); doesn't apply to steppers (no focusable input) but same "mobile-web quirks" family.

---
name: feedback-tdz-destructure
description: "TDZ traps in this repo: top-level code that reads a `const` declared later — in init(), in preview.html, and in media-module injection loops"
metadata: 
  node_type: memory

In `viewer.js init()`, **DOM button bindings that immediately call a helper destructured from `setupInteractions(...)` must be placed AFTER the destructure line**. Hoisting saves function declarations, not `const { … } = …` bindings — those are in the temporal dead zone until the destructure runs.

**Why:** Concrete incident on 2026-06-23. The chat-send-btn block was placed above the destructure and did `setSendBtn(sendBtn)` immediately. That threw a `ReferenceError: cannot access uninitialized variable`, aborted `init()` partway through, and silently broke every later listener — including the cytoscape node tap handlers. The user only saw "root node does not respond". `newCardBtn` was unaffected only by accident: its handler references `createCard` inside a click-time arrow, so the lookup is deferred until the user clicks. Commit `da6a5e2` moved the binding below the destructure.

**How to apply:**
- Default to placing helper-using bindings after the `const { … } = setupInteractions(...)` destructure.
- If a binding MUST sit above the destructure (e.g. ordering needed for something else), defer every helper reference into a closure (`() => helperFn(...)`) so the lookup happens at call time.
- When a UI control "does nothing", check the browser console first — a TDZ ReferenceError in `init()` will silently disable everything wired after it. Don't waste cycles on click-path code paths until the console is clean.

See [[chat-panel-state]] for the current placement of those bindings.

## 2026-07-11 variant: hoisted `function` closing over later `const` in preview.html

Same TDZ trap, different surface — recorded because the error message is misleading and the failure was diagnosed as a decode error before we spotted the actual cause.

`preview.html`'s `updateEvNavState(isFirst, isLast)` was written as a top-level `function` declaration (hoisted). Its body closed over `evPrevBtn` / `evNextBtn`, both `const`-declared much further down the script. The synchronous `?data=` decode branch inside `loadInitialScript` called `updateEvNavState(false, false)` *before* those `const`s had been initialised → TDZ ReferenceError. But because the call was inside a `try/catch`, the surrounding `catch` swallowed it and logged the (misleading) `preview: failed to decode ?data param` warning. The decode had actually succeeded and `loadScript` had already applied the payload — the throw only interrupted the nav-state update. Flow then fell through to `loadModuleDefault`, which overwrote the payload with `bd_V_Kolam_001`. User's symptom: "the payload never displays; the default always wins".

**Fix (commit `9e466a1`):** `updateEvNavState` looks the buttons up via `document.getElementById` at call time instead of closing over the `const` bindings. No hoisting/closure dependency on later `const`.

**How to apply this variant:**
- A `function` declaration doesn't rescue you from TDZ — its **body** still evaluates references lexically. If the body reads a later `const`, that read hits TDZ at call time.
- Alternatives: (a) look up DOM elements via `getElementById` inside the function (used here — no closure at all), (b) reorder so the `const`s are declared before the first call site, (c) wrap the earlier call site in a small deferral (`Promise.resolve().then(() => updateEvNavState(...))`) so it runs after synchronous script-body init completes. Option (a) is simplest for DOM refs since it costs one extra lookup.
- If a `try/catch` is swallowing an error that "looks like" a decode/parse failure, verify the error message actually says decode/parse. A TDZ ReferenceError inside the try produces the same fallback branch — but for a completely different reason.

## 2026-08-19 variant: module top-level loop calling a helper that reads a later `const`

Third instance, same trap — now the dominant failure mode when a media module
"loads but nothing works". `M_Fractal/music_module.html`'s `STEPPERS.forEach`
injection loop runs at script top level and calls the hoisted
`function formatDisplay(...)`. A later edit added
`const ENUM_DISPLAY = { min_pentatonic: 'pent' }` **below** the loop and read it
inside `formatDisplay`. The call resolved (hoisting); the read did not (TDZ), so
it threw on the first *enum* stepper — `scale`, the 4th of 12.

**Read the symptom set as one cause, not four.** A top-level throw in a media
module aborts the rest of the script, so you see: a partly-built control column
(exactly N rows, N = index of the first offending item), every button inert
(listeners are bound further down), AND the BD-side chrome misplaced — because
`BD_READY` is posted at the END of the module script, so BD never re-anchors the
extend panel and it falls back to its CSS default (right-hand edge instead of
the bottom-left dock slot). CSS-only changes in the same commit still apply,
which misleadingly suggests "the file loaded fine".

**How to apply:**
- Declare lookup tables/maps used by top-level init code **beside the data they
  belong to** (here: next to `SCALES` / `SCALE_NAMES`), never next to the
  function that consumes them.
- "Only the first N rows appear" in an injected list = the loop threw at item N,
  not a CSS height/overflow problem. Check the console before touching layout.
- Module iframes do NOT forward console errors to `/tmp/bd_server.log` — BD only
  relays its OWN window. Reproduce top-level order outside the browser instead:
  slice the script from its data block to the end of the injection loop, append
  the hoisted helper, stub `document.createElement`/`appendChild`, run under node.
  See [[music-player-layout]] for the module layout this bit under.

## Non-obvious technical gotchas

### 1. `<iframe>` intrinsic default height beats `position: fixed`
An iframe with `position: fixed; top: 158px; bottom: 90px` **still** renders at 150px tall because the HTML intrinsic default (300×150) wins the layout race. **Fix:** stamp `#cy.getBoundingClientRect()` values (top/left/width/height) as inline styles on `#visual-iframe` — done in both `positionCyEl()` and the init-time pin. Do NOT rely on CSS bounds alone.

**How to apply:** if the visual iframe ever mis-sizes, first check that the rect-stamping code in `positionCyEl()` is still running before rendering the module.

### 2. `params.stroke` default must be `'angle'`, not a hex colour
Kolam's hue-cycling only fires when `params.stroke === 'angle'` (checked via `angleTracked` flag). Defaulting to `'#4a9b8e'` silently disabled all colour animation.

**How to apply:** if colour appears absent from the kolam render, check `params.stroke` default in `visual_module.html`.

### 3. Initial draw must wait for layout flush
`drawWaitingMessage()` called before wrapper has real dimensions gives a 300×150 canvas. **Fix:** double `requestAnimationFrame` + `ResizeObserver` on `.canvas-wrapper`.

### 4. `.control-panel` needs `min-height: 0; overflow-y: auto`
Otherwise CSS grid child can't scroll — user could only see top 3 controls.

### 5. Symmetry engine handles arbitrary n-fold (not just the old discrete list)
`applySymmetry` divides `2π / n` and stamps that many rotations of the offscreen canvas — no assumption of "valid" values. The 2026-07-02 stepper conversion widened symmetry from `[1,2,3,4,6,8,10,12,16]` to a plain `1–16` clamp, which just works. Values like 5, 7, 9, 11, 13, 14, 15 render as valid n-fold rotations.

### 6. Closure-warning status message removed (2af5e1f)
The status line no longer surfaces the "path does not close (kolam constraint not satisfied)" warning after a render — always shows `Ready` on success. The `checkClosure()` helper is retained (dead code) in case a conditional surface is wanted later; a subsequent `bd_module`-directive-aware overlay may bring it back for scripts that flag themselves as strict kolam.

### 7. Drift state must be broadcast from `driftTick` — the parent doesn't otherwise know
`applySymmetry` / the whole render pipeline runs internally to the module; drift ticks update `angleSlider`, `angleMinutesSlider`, `angleSecondsSlider` in place. Any host harness (preview.html, BD Player mode) needs a live view of these to show drift progress in its own steppers. Fix: `driftTick` posts `bd_state_update { angle, angle_minutes, angle_seconds }` to `window.parent` every tick (5–10 Hz at low depth).

### 8. Script is user intent — drift NEVER rewrites the textarea (424a227)
Earlier iterations had the `bd_state_update` handler in preview.html also rewrite the textarea's `%%bd_angle` / `%%bd_angle_minutes` / `%%bd_angle_seconds` lines. **This was wrong.** The script represents what the user authored; drift is runtime state. Mixing them meant Copy Link captured mid-animation frames the user never chose. **New rule:** `bd_state_update` only moves the stepper display spans, not the textarea. User bakes drift into the script explicitly via ↑ (receive).

### 9. `angle_seconds` is internal-only — never appears in any %%bd_ script (424a227)
`angle_seconds` is a sub-arc-minute drift accumulator that lives only in the module's hidden `<input>`. `applyControlDirectives` no longer writes it out. `setControlValues` no longer resets the seconds slider when the incoming script omits it — that preserves the accumulator across re-renders triggered by any other directive change. Legacy scripts / the `_copy` harness path can still supply `%%bd_angle_seconds N` and it will be honoured; new scripts should never mention it.

### 10. When #9 was introduced, drift went visibly jerky — render must read seconds live from the slider (769870b)
Consequence of #9: `render()` originally computed `params.effectiveAngle` from `directives.angle_seconds` (the parsed script). Once `applyControlDirectives` stopped emitting `%%bd_angle_seconds`, that field parsed as undefined → 0. Drift only produced a visible change when minutes carried over — ~1 step per minute of arc instead of ~10/second.

**Fix:** in `render()`, read `angleSecondsSlider.value` directly (`const liveSeconds = safeParseNumber(angleSecondsSlider.value, 0)`) and use that in the `effectiveAngle` sum, not the parsed directive. Keeps script clean AND drift smooth.

**How to apply:** any future "internal-only" runtime state that render() needs must be read from its live DOM control, not round-tripped through the script text. The script is authored intent; the sliders are runtime truth.

### 11. Raw base64 in URL query strings is broken by URLSearchParams (779378c)
Raw base64 output contains `+`, `/`, `=`. All legal in URLs. But `URLSearchParams.get(name)` uses `application/x-www-form-urlencoded` decoding, which turns `+` into a literal space. So `?data=abc+def=` round-trips as `abc def=`, atob throws, receiver silently falls into DEFAULT. Cost me two rounds of "URL looks fine but nothing renders" before I saw it.

**Fix:** always wrap the base64 with `encodeURIComponent()` when embedding in a URL. `+` → `%2B`, `/` → `%2F`, `=` → `%3D`. URLSearchParams auto-percent-decodes on the receiving side back to raw base64; atob works. Applied at three encoding sites: viewer.js Copy Link (?data=), preview.html Copy Link (?script=), preview.html buildBdReturnUrl (?data= to graph.virtualfictions.uk).

**How to apply:** if a new Copy-Link-family button is ever added, `?<name>=${encodeURIComponent(base64)}` — never `?<name>=${base64}` bare. Same rule for hash fragments.

### 12. `activeNodeId` ≠ last-read node — Copy Link wants `lastReadNodeId` (3058633)
`activeNodeId` inside `setupInteractions` is only assigned by navigation entry points (`expandToNode` / `expandToFamily` / `expandChildLevel` / `restoreState`) — i.e. by double-tap or programmatic view change. A single tap that just reads a node routes through `routeNodeText` and never touches `activeNodeId`. So if a user is inside a Cluster and single-taps a child TextNode to read it, `activeNodeId` is still the Cluster.

But `lastReadNodeId` (and its sibling `lastReadNodeCy`) IS set by `markReadNode`, which fires on every read tap (both youCy chip taps and main-graph taps). That's the correct source for "which node is the user currently reading."

**Fix:** Copy Link handler tries `getLastReadNodeId()` first, falls back to `getActiveNodeId()` only if nothing has been single-tapped yet. Both are exported as getters from `setupInteractions`.

**How to apply:** any future "grab context from the current node" feature should prefer `lastReadNodeId` over `activeNodeId`. `activeNodeId` is a navigation cursor; `lastReadNodeId` is a reading cursor. They are not the same thing.

Commits `3fef0b7` → `c6bd547` → `6828974` → `6773772`. Enables a user in the BD viewer to copy a URL that opens the current panel/card content in the standalone kolam player elsewhere (phone, other tab, notes app).

**Payload envelope (the BD ↔ standalone contract):**
```
?data=<base64 UTF-8 of JSON.stringify({ script, node_url, source_text, title })>
```
- `script`   — full panel/card text; precedence in viewer.js = focused local-card textarea → `topLocalCard().body.value` → `#default-card-body` `textContent`.
- `node_url` — UUID `url` property of currently focused graph node (from `activeNodeId` → `cy.getElementById(activeNodeId).data('url')`), or `null` if no node focused.
- `source_text`, `title` — same source; both null when no node focused.

Encoding uses classic `btoa(unescape(encodeURIComponent(JSON.stringify(payload))))` per user's spec — matches what standalone-side `b64DecodeUtf8` reverses.

**Why the extra fields.** `node_url`/`source_text`/`title` are context for a future **"back to BD" round-trip** — the standalone player will consume them to offer a "return to the originating graph node" affordance. Not consumed yet; on the standalone side they stash on `window.bdReturnContext` after `?data=` decode, and are console.log'd for dev inspection.

**Standalone-side decoder (preview.html `loadInitialScript`).** Precedence:
1. `?data=<base64 JSON>` — BD viewer envelope. Decodes to `{ script, node_url, source_text, title }`; script populates textarea; other three fields → `window.bdReturnContext`.
2. `?script=<base64 raw>` — legacy standalone-Copy-Link URL (still emitted by preview.html's own Copy Link button).
3. `DEFAULT_SCRIPT` — symmetry 3, deliberately unusual so a default fall-through is visually distinguishable from a successful param decode during testing.

# Always-on chat + Join/Leave (2026-07-15)

Live on `origin/main` at commits `893e9af` (UX simplification) → `fd43b45` (onboarding line). Reverses the earlier decision (see [[mm1-amendment]] "Pair button removed") to fold pair-queue behaviour into the Chat toggle — turns out that overloading made "just try Player" or "just browse the chat" impossible without also queueing for a partner.

**Why:** On arrival, users could browse the graph but not use Player mode (radios disabled) or see the chat panel (hidden) until they pressed Chat — which also queued them for pairing. Users who wanted to try Player or just read system status were forced through the pair-queue flow. Reframing: chat panel is a permanent "communication window" that carries system status / help / (future) bot-buddy dialogue / real partner cards; human pairing is a separate opt-in via a dedicated Join / Leave button.

**How to apply:** When touching pair or chat-mode logic, remember there is no chat-mode toggle any more. `chatModeActive` is initialised to `true` at module load and never flipped. All the old gates (Player radios, Copy Down, EV invite panel) are unlocked at boot. Only `pairingState.active` / `pairingState.waiting` gates human-pair-specific behaviour.

## What the user sees now (fresh page load)

1. Chat panel visible immediately. Server sends the how-to system card + status card + `chat_ready` → client creates visible N=1 local card above them. Nodes / Player radios enabled; EV "Extend / Jump to / Copy Link to External Website" panel appears the moment Player is picked. Top-right button reads **Join**.
2. Press **Join** (optionally with a curation code in `#dev-code`) → button flips to **Leave**, `#pair-status` reads "Waiting..."
3. On successful pair → both sides flip to **Leave** / "Paired"; partner cards start flowing into the same chat panel that already holds the system cards.
4. Either side presses **Leave** (or their tab closes) → the other side reverts to **Join** / status blank; "Partner disconnected." card lands in the chat panel. **No auto-requeue** — user presses Join again if they want to try another partner.
5. `pair_denied` (`code_required` or `same_device`) leaves chat panel active — only the pair state resets. User adjusts and presses Join again.

## Non-obvious gotchas

### AC-G1. `chatModeActive` initial value is now `true` at module load
The variable is declared `let chatModeActive = true` at module scope — before `init()` runs. If any early code path (before ws connects) checks it, they see `true`. In practice this is fine because early check sites (`routeNodeText`, `positionCyEl`) are only reachable via user interaction after DOM is ready, but if you add a new early-boot code path that keys on `chatModeActive`, be aware.

### AC-G2. Boot activation block calls `positionCyEl` inside `requestAnimationFrame`
`chatPanel.classList.add('active')` changes the panel from `display: none` to `display: flex`, so cy's top-anchor calculation needs a rAF to see the correct panel rect. Skip the rAF and cy pins to the wrong y-coordinate on first paint.

### AC-G3. Button label is set from state, not from `togglePair` action
`updateJoinButtonLabel` derives label from `pairingState.active || pairingState.waiting`. `togglePair` mutates state then calls it. All four message handlers mutate state then call it. Don't hand-set `chatBtn.textContent` anywhere else — race with the helper.

### AC-G4. No `leave_chat` emit anywhere
Under the previous chat-toggle model, chat-off sent `leave_chat` → server dropped "Partner left chat" system card into buddy's log. Now chat is never left; the equivalent user action is Leave → `unpair`, which triggers "Partner disconnected." via the server's unpair handler. `leave_chat` handler on the server is dead but not removed (kept for defensive read; harmless).

### AC-G5. Auto-requeue removed
Previously `buddy_disconnected` handler auto-emitted `ready_to_pair` if chat was still active. Now user goes back to Join button; must press manually to re-queue. Matches user's stated "opt-in to unpair" model — opt-in both directions.

### AC-G6. `pair_denied: same_device` behaviour subtly clearer now
Under old model, this reason was the ONE that kept chat active (for solo composition); other reasons closed chat. Under new model ALL reasons leave chat active (chat is always on). The `same_device` branch in the message handler no longer needs its special-case behaviour — collapsed into common path.

## Non-obvious gotchas

### G1. `disableLosslessIntegers: true` matters
Without it Neo4j Integer values arrive as `{low, high}` objects, breaking JSON stringify + comparisons. Enable on the driver instance.

### G2. `DUMP DATABASE` output column is `QUERY` (uppercase)
Memgraph returns each statement in a column named `QUERY`. Older docs sometimes say `query`. Tool handles both to be safe. If your version differs, sanity-check the record shape via a small `cypher DUMP DATABASE` first.

### G3. Server-side `helpersByName` is loaded once at boot
No hot-reload endpoint. Sync + restart is the loop. If wording iteration ever gets tight enough that restarts feel slow, add a `msg.type === 'reload_helpers'` handler on the server that re-calls `loadHelpers()`. Guard by curation code.

### G4. sendHelperByName missing-key path is silent-except-log
If a helper name is mistyped in server.js OR the .md hasn't been synced OR the DB is empty, the send silently skips — logs `[BD] sendHelperByName: no such helper "<name>"…`. Users see no card. Watch `[BD] Loaded N helper messages from DB` at boot to sanity-check that N matches the .md.

### G5. `pingMemgraph().then(loadHelpers)` is fire-and-forget
Server starts listening before helpers finish loading. First user connect could in principle race the load. In practice loadHelpers is one Cypher round-trip in milliseconds; the race window is small. If it ever bites, await the chain before `server.listen`.

### G6. `Partner joined chat…` at server.js:656 is left in place but dead
enter_chat's `if (buddyId && inChat.get(buddyId))` branch never triggers under always-on-chat (enter_chat only fires at boot, before any pairing). Not migrated to a Helper — deciding whether to resurrect or delete is a future call.

### G7. `statusTextFor()` is dead but retained
Same reasoning — was called from enter_chat, now unreached. Its two string branches ("You're chatting…", "Partner not available…") are candidates for future Helper messages if we ever want them.

## 2026-07-17 amendments — @flag review workflow + :User retirement + nav-nodes dump

Live on `origin/main` from commits `540b46b` → `de85344` → `fbad529` → `f36cd78`.

### `@flag update_this` gate on both sync-helpers and write

New directive `@flag update_this: true|false` recognised by BOTH `sync-helpers` (per @hub/@helper block) and `write` (per @match/@set block). Semantics:

- **CREATE** (node doesn't exist in DB) → always applied, no flag needed. Adding a new block to the .md just works.
- **UPDATE** (node exists) → only applied when `@flag update_this: true`. Otherwise skipped and reported as skipped in the JSON output + `[bd_tool] … : created N, updated M, skipped K` summary line.
- **Auto-reset after apply** — successful CREATE or UPDATE causes the flag line to be rewritten to `false` in the .md (existing flag line replaced in place; missing flag line inserted after the last directive). Prevents accidental re-apply on next sync.

Rationale: explicit-intent gate for bulk review workflows (hundreds of blocks, edit a few). Prevents accidental writes from noise (paste-into-wrong-block, autocorrect drift, etc.).

### `write` extended to multi-block

Replaces the old single-block parsePatch with `parsePatchesFile` — same @match/@set/@flag directives, one or many blocks separated by `---`. Identity now considers `@match title` as a fallback after url + name (needed for section-title TextNodes which have title but no name).

### :User node retirement — viewer_id in-memory

Retired the pattern of creating a `:User` node in Memgraph on every socket connect. Previously the server ran `CREATE (u:User {…}) … SET u.viewer_id = 'N_' + toString(id(u))` to inherit an integer id — but the DB node was a means-to-an-end for an in-memory-only concern, and leaked ~42 orphans across dev iterations when purge timers died with their process. Now viewer_id derives from `crypto.randomUUID().split('-')[0]` — 8 hex chars, globally unique, no id() footgun.

Also added `purgeStaleUsers()` in the boot chain (`.then(purgeStaleUsers).then(loadHelpers)`) that runs `MATCH (u:User) DETACH DELETE u` once at startup. One-off cleanup for the 42 accumulated orphans; a cheap no-op on every subsequent boot now that no `:User` is ever created. Defensive against a class of bug rather than an ongoing leak.

**Principle codified by user 2026-07-16:** "no nodes in Memgraph for non-obvious architectural reasons".

### Memgraph id() vs elementId() gotcha (verified today)

User's warning materialised: my first backfill-urls draft used `elementId(n)` (Neo4j only). Memgraph doesn't implement elementId — has to use `id()`. **AND** id() returns a numeric identifier that shares its space with relationship ids, so a bare `WHERE id() = X` could false-match. Rule: always scope the MATCH pattern to nodes only via `MATCH (n)` before the WHERE clause, so a rel id can't slip through.

Corrected form used throughout bd_tool.js write/backfill:
```cypher
MATCH (n) WHERE id(n) = $nid SET n.url = $url
```
NOT `MATCH () WHERE id() = X`.

## New gotchas to record

### G8. Memgraph doesn't implement elementId()
Neo4j-only function. Memgraph parse error: `Function 'elementId' doesn't exist`. Use `id()` — but scope MATCH to nodes-only patterns to avoid the node/edge id-space overlap (see [[deep-link-v2-moderation]] G1 for the related elementId-was-not-durable revert).

### G9. `id()` node/edge id-space overlap
A node's `id(n)` can numerically equal a relationship's `id(r)`. The MATCH pattern's shape scopes the search — `MATCH (n)` only matches nodes; `MATCH ()-[r]-()` only matches relationships. Never rely on `id()` alone to distinguish; rely on the pattern.

### G10. sync/write flag auto-reset uses REPLACE-in-place for existing flag lines
Existing `@flag update_this: true` lines are OVERWRITTEN at their exact line index (no shift). Missing flag lines are INSERTED after `lastDirectiveLine` (shifts subsequent lines). Both operations happen per-block; blocks processed in reverse lastDirectiveLine order so later-block inserts don't shift earlier-block indices.

# One-tap chunked node reading UX (2026-07-23 → 2026-07-24)

Big pivot from the old single-vs-double-tap gesture model to a unified "every tap advances" flow. Live on `origin/main` from `f59f3de` (the main pivot commit) with an earlier stepping-stone at the boot-helper sequencing work that was superseded.

## The user-facing model

Every tap on a main-canvas node advances a per-node reading sequence:

- Tap 1 on fresh node → chunk 0 shown as its own system card at top of chat stack
- Tap 2 on same node → chunk 1
- Tap 3 → chunk 2
- Tap past last chunk on a node WITH descendants → navigates in (equivalent of the old double-tap)
- Tap past last chunk on a node WITHOUT descendants → silent no-op after the "no further descendants" hint (or a redisplay depending on how it happened)
- Tap a different node → resets the sequence to the new node's chunk 0

The 320/560 ms defer windows are gone. Every tap fires immediately. **Breadcrumbs untouched** — those still use the pre-existing single-tap-defers-then-double-tap-navigates model.

## The `%%bd_` directives

Two new inline directives on nav-node text (all live in the node's `text` property, stored in Memgraph):

- `%%bd_chunk` on a line by itself → chunk boundary. Empty leading/trailing/double-marker chunks are filtered.
- `%%bd_hint <one-line text>` → author-controlled hint for the containing chunk. Anywhere in the chunk (typically last line). Extracted and removed from the displayed body.

If a chunk has no `%%bd_hint`, an auto-injected fallback fires from the `getChunkHint(isLast, hasDescendants)` helper:
- Non-last chunk → "Tap for next message from me."
- Last chunk, has descendants → "Tap once more to see connected nodes."
- Last chunk, no descendants → "There are not yet further descendants."

Author overrides the fallback where copy needs to be specific (plural/choice/situational). Un-updated nodes keep working via the defaults — no bulk edit needed.

## What renders

Each chunk is its own **`{ kind: 'system' }`** card in the chat stack — one per chunk, prepended (newest-on-top, BD's stack convention). Not the old textarea-append into the top local card, because textareas can't do inline centring for the hint.

Card structure:

```html
<div class="card system">
  <div class="card-head">
    <span class="card-head-label">ButterflyDreaming (0)</span>
  </div>
  <div class="card-body">
    <div class="chunk-text">…chunk body, bot-blocks processed, name/idx prefix already in head not body…</div>
    <div class="chunk-hint">…centred italic amber hint…</div>
  </div>
</div>
```

CSS in `style.css` under `.card.system .card-body .chunk-hint`: `text-align: center; color: #c8a050; font-style: italic`. No margin between chunk-text and chunk-hint — flows straight below.

Head label numbers chunks 0-based: `<name> (N)`.

## Trade-off worth naming

Chunks stack newest-on-top per BD convention → **multi-chunk sequences read in reverse chronological order** in the panel (chunk 2 above chunk 1 above chunk 0). Not a story problem for 2–3 chunk nodes (each card is self-contained with its numbered head), but if a node grows to 5+ chunks it may feel jarring. ## Non-obvious gotchas

### G1. `hasNavDescendants` MUST be direction-agnostic (`connectedEdges`, not `outgoers`)
The CF/SF replacement loops in the graph load path (`viewer.js` around the main-graph → clusterFamily → subfamilyLinks fetch chain) force `Cluster ↔ Family` and `Family ↔ SubFamily` edge source/target to canonical sides regardless of DB storage direction. So from a SubFamily's Cytoscape perspective, ALL its DESCENDS_FROM edges come out as incoming — `outgoers` returned zero for every SubFamily and wrongly said "no further descendants".

### G2. Chunk cards live outside `setChatText`'s append flow
`setChatText` targets the top local textarea (appends to it). Chunk cards intentionally BYPASS setChatText and go direct to `createCard({ kind: 'system', label })` because their body is a div (with inner `.chunk-text` + `.chunk-hint`) that needs HTML-level structure. Any future "one accumulating card per session" change would need to reintroduce append logic — but on a div, not a textarea.

### G3. Empty-text + no-descendants nodes need a visible response
When a node has neither text nor descendants, silent tap = confused user. The chunk 0 fallback in `advanceOrNavigate` sets `readingState.chunks = [{body: '', hint: null}]` so the `getChunkHint(true, false)` default hint fires — the "There are not yet further descendants." card gives visible acknowledgement.

### G4. `primeRootReading` is idempotent by chat_ready trigger
`handleChatReady` calls `primeRootReading` — which calls `advanceOrNavigate` on the Root node. `advanceOrNavigate` is idempotent for same node (returns early if readingState already has that nodeId at same chunkIndex). But repeat chat_ready events would advance the chunk. Only one chat_ready fires per socket, so this hasn't been a problem, but if it becomes one, guard in `primeRootReading` with `if (readingState && readingState.nodeId === rootNode.id()) return`.

### G5. Head label carries the source anchor now, not the body
Before, the body text was `<name> (N): <chunk_text>` — inline prefix. Now the head shows `<name> (N)` and the body is just the chunk text (bot-block-processed). Cleaner separation but consumers of `card.text` (e.g. `handleCardCopy`) see body-only + hint-only text without the source anchor. If ever needed, `card.text` set-site can prepend the label.

Four follow-ups landed same day as the main pivot — the shape of the model didn't change, but readability did:

1. **Breadcrumb chips → single-tap navigate.** Same one-gesture model as main canvas. Retired 8 timer/pending state slots (buddy/you × Touch/Desktop × Pending/Timer). Chip's underlying node becomes the centre.

## More gotchas from the polish batch

### G6. Inline `el.style.opacity` on cards defeats class-based dimming
Every card gets `el.style.opacity = 0.85` set inline by `createCard` (from `card.volume`, which was some legacy per-card intensity slot). **Algorithm (line-walk, per user question — no blank line above needed):**

1. Find the LAST line matching `/^%%bd_module\s+\S+/` in the input.

## Key implementation subtleties (worth remembering)

- **DFS shared-prefix**: iter N and N−1 emit the same first L(N−1)
  symbols. Without the skip mechanism, bumping iterations wouldn't
  change what a user hears from the start.
- **Peano self-similarity**: even after skip, first ~10 notes have
  the same delta shape at different iterations. Fix: seed the pitch
  reflection walk from raw-y (mod scaleLength) so different starting
  raw y positions produce different opening scale degrees.
- **Tonic scan**: seeded reflection makes iter 2 start on E, iter 3
  on G, etc. Musically odd. Scan forward to first horizontal at
  effective y ≡ 0 (tonic) so every iteration opens on the root.
- **Octave clamp**: %%bd_root suffix clamps to keep tonic in
  MIDI [33, 96] → notes fit within full piano [21, 108]. User's
  original ask was "piano minus 1 octave each end" but that clamp
  was too tight and rejected C,,. Loosened to full piano safety.
- **Chord octave spread**: p2 shifted −12, p3 shifted +12 for
  3-octave chord span. Fold back to unshifted if the shift would
  push a note off piano.

name: ingest-workflow
description: "Repeatable pattern for ingesting a text work (poem, story) into Memgraph — Gateway + Section-title + N chunks + Cluster assignments + weights + the post-ingest n_r refresh that bulk inserts otherwise skip."
metadata:

Repeatable pattern for ingesting a new text work (a poem, a short story) into the BD graph. First codified on 2026-08-01 when adding "Dreaming of Li Bai" (Du Fu, 759 CE). See `du_fu_ingest.js` in the repo root — kept as a self-documenting template — and `du_fu_plan.md` as the design-doc precedent.

## Node schema for a work

Every text work is a small local graph of `:TextNode`s:

| Kind | Properties |
| --- | --- |
| **Gateway** | `gateway: true`, `section_title: false`, `seq: -1`, `source_text: "<Work Name>"`, `text` = about the work (author + translator + gloss) |
| **Section-title** | `gateway: false`, `section_title: true`, `seq: 0`, `source_text: same`, `title: "<Piece Name>"`, `text` = about this piece (date + brief context) |
| **Content chunk** | `gateway: false`, `seq: 1..N`, `source_text: same`, `title: <same as Section-title's title>` **(REQUIRED — else the node label falls back to `source_text` instead of "`<seq>: <piece title>`"; the 2026-08-17 Du Fu bug)**, `text: <chunk>` — **no `section_title` property at all** (matches Tao Te Ching corpus convention; storing `section_title: false` breaks convention and would trip verify queries that filter on `IS NULL`) |

Each content chunk's text ends with a bare `%%bd_hint` line. This suppresses the auto-injected tap hint under the chunk — chunks are read directly via the layout-reading grid ([[chunked-ux]] snake view), not tapped through sequentially, so the hint would mislead.

## Edges within the work (structural)

- Gateway `-[CHILD]->` Section-title *(drilling past the gateway's chunks lands on the title)*
- Section-title `-[CHILD {source:'sequence', weight:0.75}]->` Chunk 1 *(start of the reading chain)*
- Chunk n `-[CHILD {source:'sequence', weight:0.75}]->` Chunk n+1 *(the reading chain; title→1→2→…→N)*
- Each Chunk `-[PART_OF]->` Section-title *(snake view enumerates via this back-ref)*

**CORRECTION 2026-08-17:** the CHILD reading chain (title→1→2→…→N, each hop
`source:'sequence', weight:0.75`) is **REQUIRED** — earlier versions of this note
(and `du_fu_ingest.js`) said "chunks are leaves, no CHILD chain," which left
**Poems of Du Fu** the ONLY work without a forward reading spine. Every other work
(Tao 81, Zhuangzi 50, Grimm 30, Hardy 17, Leaves 10) has it. The chain powers the
seq-navigation and the reading-spine amber forward-arrow ([[unified-focus]] —
`applySeqSignals` styles the central node's outgoing CHILD hop). Fixed Du Fu
retroactively + updated the template.

## Edges to Clusters

- Gateway `-[CONTAINS_CLUSTER {count}]->` Cluster — `count` = number of chunks under this gateway touching this cluster; auto-derived from the sum of chunk memberships.
- Chunk `-[CLUSTER_REL {tagged_as|resonates_with|bridges_to|echoes|gives}]->` Cluster — each edge carries any subset of the five weight properties, each `0.0`–`1.0`. See [Note on Cluster-Textnode edges.md](../../butterflydreaming_graphviewer1/Note%20on%20Cluster-Textnode%20edges.md) for what each weight means. **Never store a zero weight** — omit the property instead (viewer treats absent = 0, but persisted-zero is misleading).

## Workflow

1. Draft a plan `.md` in the repo root (like `du_fu_plan.md`) covering: chunks, chosen Clusters, weights, gateway/section-title copy. User approves/edits.
2. `node bd_tool.js backup` — always, before any DB mutation ([[backup-safety]]).
3. Copy `du_fu_ingest.js`, adapt the `WORK` constant + `chunks` array + copy + weights.
4. Run the script.
5. **Post-ingest: refresh `n_r` on affected Clusters.** Server-side `edit_save` does this automatically on single-edit paths, but bulk-insert scripts bypass it and leave the badge counts stale. Query template:
   ```cypher
   UNWIND [<cluster names>] AS name
   MATCH (c:Cluster {name: name})
   OPTIONAL MATCH (n:TextNode)-[:CLUSTER_REL]->(c)
   WITH c, n WHERE n IS NULL OR (n.gateway = false AND n.section_title IS NULL)
   WITH c, count(n) AS total SET c.n_r = total RETURN c.name, total
   ```
6. Delete the per-work `.js` after use, or keep as a per-work record — the plan `.md` is the durable design doc.

## Why / How to apply

**Why:** consistent schema per work lets seq-navigation, the reading-spine amber arrow, chunk hints, cluster badges, and cross-work navigation all work uniformly. The CHILD reading chain (title→1→2→…→N) is part of that consistency — omit it and the work has no forward reading spine (the Du Fu bug). (The old note claimed the CHILD chain "breaks the snake-view leaf-node model"; that predates [[unified-focus]] — the chain is now required.)

**How to apply:** when user asks to ingest a poem or text piece:
- Confirm with them if it's a new gateway (new author/collection) OR adding a piece to an existing gateway (in which case the gateway node already exists; only add section-title + chunks + edges, and increment CONTAINS_CLUSTER counts on the gateway rather than creating new ones).
- Ask their preference for how to pick Clusters ([[dev-panel]] curation code needed only for UI-driven edits; direct script ingest doesn't check it).
- Draft the plan `.md`, get approval, then execute per the workflow.
- **Always** refresh `n_r` in step 5 — easy to forget, breaks the badge counts silently.

Related: [[chunked-ux]] for the chunk/hint rendering rules, [[dev-panel]] for the code-gated in-UI editor that handles single-edge edits (which do auto-refresh `n_r`).

every pass computes the same geometry.

- Rotation: measurements taken while `#rotate-to-portrait` is showing are

User "restarted" the server multiple times and saw no new log output; turned out an earlier `node server.js` process was still bound to 8080, and every "restart" was silently EADDRINUSE-crashing before printing anything. Any browser tab was still hitting the ghost. `lsof -ti :8080 | xargs kill` cleared it. **How to apply:** if editing server-side code and no logs / behaviour change, first `lsof -i :8080` before assuming anything about the JS side.

### 14. `#visual-iframe` must NOT have hardcoded `src` in HTML (2026-07-05)
Originally `<iframe id="visual-iframe" src="/visual1/">` — iframe started loading before viewer.js could attach any BD_READY listener, so BD_READY fired to no listener. But `currentModuleId` reverse-lookup (matching iframe.src against registry) then said "already loaded" → `loadModuleForNode`'s fast-path postMessage → iframe silently drops it because inner module hasn't installed its own message handler yet. **Fix:** remove `src=` from HTML entirely; `loadModuleForNode` owns the URL and the first load always goes through the swap-and-await-BD_READY path.

### 15. Relay's `RELAY_UP` must include BD_READY (V_Kolam/index.html)
Original relay explicitly excluded BD_READY to prevent internal signal leakage. That was fine when the viewer never needed BD_READY (preload assumed). Under MM1.6 the viewer's `onReady` listener waits on BD_READY forwarded through the relay — without the RELAY_UP addition, the wait never resolves and the initial `bd_script_update` is dropped. **Fix line:** `RELAY_UP = new Set([..., 'BD_READY'])`.

### 16. `setChatText` must be preceded by synchronous `handleChatReady()` when scripting chat entry
`toggleChatMode` only calls `ensureLocalCard` which creates a HIDDEN N=0 ghost card. The VISIBLE N=1 card is created by `handleChatReady` — normally on the server's async `chat_ready` message. If a synchronous return-flow calls `setChatText` between those events, the text lands in the ghost and the later server-driven `handleChatReady` creates a fresh empty N=1 above it. **Fix:** call `handleChatReady()` synchronously before `setChatText()`; the later server-driven call is idempotent (no-op when top is visible).

### 17. `positionCyEl` must skip the iframe rect-stamp when cy has zero dimensions
`toggleChatMode` schedules a trailing rAF that calls `positionCyEl()`. In the return-flow, `setViewMode('player')` has run first and hidden cy. `#cy.getBoundingClientRect()` returns all zeros for `display:none` — stamping those onto the iframe's inline styles collapses it to 0×0 and the inner module renders into a zero viewport (blank surface). **Fix:** guard `if (cyRect.width > 0 && cyRect.height > 0)` around the stamp; the last non-zero stamp remains authoritative across rAF ticks while cy is hidden.

### 18. `toggleChatMode`'s rAF cy.resize/cy.fit must guard against hidden cy AND fit only visible elements
Same rAF as #17: `cy.resize()` on a display:none container zeroes cy's internal size, and `cy.fit(undefined, ...)` fits ALL elements' bounding box (hidden ones' layout positions still exist), so the earlier `expandToNode(target)`-driven fit gets clobbered. When user later exits Player mode to Nodes, cy re-appears framed around the whole-graph bounding box centered near Root instead of the target. **Fix:** skip resize/fit when `cyEl.classList.contains('hidden')`, and change `undefined` → `cy.elements(':visible')` so partial views don't leak hidden-node bounds. Complement in `setViewMode('nodes')`: rAF `cy.resize()` + `cy.fit-to-visible` on exit so cy re-syncs after having been hidden.

## Virtual "position 0" for ?data= arrivals

When EV loads with `?data=<payload>`, the payload is cached as `virtualStart = {script, node_url, source_text, title, name}` and `atVirtualStart = true`. Navigation table:

| position | source | ◀ | ▶ |
|---|---|---|---|
| 0 (virtual) | ?data= payload | disabled | → `/api/module-default` → first DB sibling |
| 1 | `bd_V_Kolam_001` | → virtual | → position 2 |
| 2 | `bd_V_Kolam_002` | → position 1 | disabled if module has 2 nodes |

**Key rule:** when `virtualStart` exists, server-reported `isFirst` is overridden to `false` for all DB positions (virtual is always before). ◀ from a DB position where server says isFirst → returns to virtual (calls `goToVirtual()` helper).

`goToVirtual()` re-plays `loadScript(virtualStart.script, {…})` and sets `atVirtualStart = true`. Any manual textarea edits made at the virtual position are LOST on Prev/Next away (virtual is a snapshot, not live).

**Enter BD (from EV):** always uses the current position's node_url + script. On virtual → returns to the arrival node with the edited script. On a DB position → returns to that DB node with its DB script (or with any manual edits since navigation).

## `loadScript(script, meta?)` — central function

Called by initial-load (?data= / ?script= / DEFAULT / fetch), Prev/Next, and any other script-update path in the EV. Sets textarea, syncs steppers, posts `bd_script_update` to module (or queues in `pendingScript` until BD_READY), updates `currentScript`/`currentNodeUrl`/`currentSourceText`/`currentTitle`/`currentName`, calls `renderSourceContext()`, and silently clears `frozen` state (fresh script means the old preFreezeAngleDrift is stale).

## Non-obvious gotchas

### 21. `updateEvNavState` TDZ throw silently swallowed the ?data= payload (9e466a1)
Symptom: URL with ?data= displayed bd_V_Kolam_001 (module default) instead of the payload's script. Console: `preview: failed to decode ?data param  ReferenceError: Cannot access uninitialized variable`.

Cause: `updateEvNavState` is a `function` declaration (hoisted), but its body closed over `evPrevBtn` and `evNextBtn`, both `const`-declared much later in the file. When `loadInitialScript`'s ?data= branch called `updateEvNavState(false, false)`, those `const` bindings were still in TDZ → ReferenceError. The surrounding try/catch caught it (misleading "failed to decode" log; the decode had actually succeeded and loadScript had already put the payload in the textarea), and the flow fell through to `loadModuleDefault`, which overwrote the payload with `bd_V_Kolam_001`.

**Fix:** `updateEvNavState` now looks buttons up via `document.getElementById` at call time. No closure dependency on the `const` bindings. See also [[tdz-destructure]] for the general pattern.

### 22. BD viewer's ?data= handler must resolve module-id lookup structurally, not by name
Old fallback: `cy.nodes().filter(n => n.data('name') === moduleId + '_1')`. Would break on any naming change (e.g., `_1 → _001`). Replaced with `hasModuleScript === moduleId || parseModuleId(text) === moduleId`, then min(seq). See "Structural default-node lookup" above.

### 23. LIMIT 2 idiom for sibling+boundary in one query
`/api/module-sibling` uses:
```cypher
MATCH (n:TextNode) WHERE n.hasModuleScript = $module AND n.seq ${op} $currSeq
RETURN n ORDER BY n.seq ${order} LIMIT 2
```
If 0 rows → boundary. If 1 row → sibling AND we're at the boundary in that direction. If 2 rows → sibling AND there's more beyond. Response's `isFirst`/`isLast` derived from this + the direction (we KNOW there's something on the other side, since we came from there).

### Cross-tab kick (server-driven, cookie-based)

Per-browser bd_device_id cookie (7-day Max-Age, UUID value). Server maintains `deviceIdToWs: Map<deviceId, ws>`. On any new WebSocket connection whose device_id matches an existing entry, server sends `{type: 'kicked_by_newer_tab'}` to the old ws then closes it. Client handler shows a specific session-expired overlay ("Another BD session opened on this device…").

Scenario: BD tab A → Jump to opens EV in tab B → in EV, Jump In navigates tab B to BD with ?data=. Tab A's ws gets kicked at the moment tab B's ws upgrades. Result: only tab B is live.

**Why cookies over BroadcastChannel:** BroadcastChannel is same-origin, so it'd break the moment EV moves to GitHub Pages (BD origin ≠ EV origin). Cookies belong to BD's origin and travel with every WS upgrade to BD regardless of where the browser navigated from. Works across the EV-on-different-origin future.

**"Some trouble" bypass** (per user's acceptance bar): clear cookies, use incognito, or a second browser. Wifi + cellular is fine (different browsers). No tighter than that.

## Non-obvious gotchas

### 24. Cookie only issued on top-level HTML requests, not on every asset (server.js)
Guard: `if (req.path === '/' || req.path === '/index.html')`. Without this, parallel image/JS/CSS requests during the first page load would each see no cookie and each generate a Set-Cookie with a different UUID; browser would race and end up with whichever response arrived last. Only issuing on HTML entry means one request, one cookie, no race.

### 25. `deviceIdToWs.delete` must identity-check the map entry
```js
if (ws.deviceId && deviceIdToWs.get(ws.deviceId) === ws) {
  deviceIdToWs.delete(ws.deviceId);
}
```
Without the `=== ws` check, a fast kick+reconnect sequence could leave the map briefly empty: new ws replaces map entry → kicked-ws's own `close` event fires later → naive delete clobbers the replacement. The identity check ensures we only delete when the map still points at the ws that's closing.

### 26. positionCyEl aspect-ratio guard for the iframe reserve
Landscape (`innerWidth > innerHeight`): reserve 100 px on the right of the iframe for the invite panel. Portrait: reserve 0 (panel repositions to bottom-right via CSS and overlays the iframe there). Without the guard, phone-shaped viewports would leave a suspicious empty band on the right of the visual.

### 27. `body.player-active` is the only CSS gate for the invite panel
Not `body.chat-mode-active`. Player mode implies chat-mode is active (you can't enter Player without Chat), but the reverse isn't true (Chat can be on without Player). The panel is scoped to Player mode specifically since that's when the visual iframe is showing.

### 28. New tab (`window.open(url, '_blank')`) preserves BD session
User asked for new tab so the BD chat/pair session survives the Jump-to. If we ever switch to same-tab navigation (`window.location.href = url`), the WebSocket dies and the pair tears down — non-recoverable without full page reload. Worth flagging if the button is ever re-wired for a same-tab flow.

### 29. Canvas-snug-against-column via justify-content: flex-end
`.canvas-wrapper` in V_Kolam/visual_module.html previously had `justify-content: center` which left a large empty gap between the square canvas and the fixed-220px control-panel on wide viewports. Flipped to `flex-end` on landscape (portrait media query overrides back to `center` since the layout stacks column-direction there and horizontal alignment doesn't apply the same way).

```markdown
---
name: perf-knobs

Two levers govern the chat panel's perceived responsiveness. Treat them as tuning knobs, not invariants.

## 1. Click / tap debounce (currently set, easy to nudge)

The single-click → text-display path is gated by a debounce timer that waits to see if a second click arrives (would mean double-click → navigate via `handleNodeTap`). All 8 debounce sites in `viewer.js` use the same two values:

| Path | Was | Now (commit `2f3fa5f`) |
|---|---|---|
| Desktop click → text | 450 ms | **320 ms** |
| Touch tap → text | 800 ms | **560 ms** |

Network is NOT in this path — text lives in `node.data()`, populated at page open. The entire wait is the debounce. So the value directly tunes "click → text visible" latency.

**How to apply:**
- All 8 sites use bare `, 320)` or `, 560)` literals — `grep -E ", (320|560)\)" viewer.js` enumerates them.
- To bump: edit globally via `replace_all`. Don't change one site without the others — they're meant to stay in sync (one is the canonical debounce, the others are per-bar variants).
- If double-taps start feeling unreliable on touch (older fingers, slow taps), bump touch (560) first.
- Next comfortable step if more snappy is wanted: **280 ms desktop / 480 ms touch**.

## 2. Initial-load size — the lazy-text-fetch ceiling (not yet built)

Currently the page-open WS query is `MATCH (n)-[r]->(m) RETURN n, r, m` ([viewer.js:3118](viewer.js#L3118)) — pulls every node's full properties, including `text`. Cytoscape ingests it all into `node.data()`. All subsequent navigation is a visibility filter; no network involved.

**Why this is fine today:** the graph is curator-authored (low thousands of nodes max for the foreseeable horizon). Initial load is fast, navigation is instant, bot-context display is local.

**Rough scaling thresholds on iPhone Safari:**

| Node count | Initial load | iPhone memory | Verdict |
|---|---|---|---|
| < 1,000 | snappy | trivial | current is ideal |
| 1k–5k | 1–3 s | low single-digit MB | fine; first paint slows |
| 5k–20k | 3–10 s | tens of MB | wait noticeable; tap latency still good |
| 20k+ | 10 s+ | hundreds of MB | risk of Safari eviction on backgrounding |

**The trigger for action:** initial load on iPhone Safari exceeding ~3 seconds. Until then, don't refactor.

**When the trigger hits — the cheapest refactor:**

Separate "identity / structure" (always loaded) from "text" (lazy):

1. Server: change the initial query to exclude `n.text` (and any other heavy properties). Add a new `get_node_text` WS message that returns just `{nodeId, text}` for a single node.
2. Client: in `routeNodeText`, before `buildTooltipContent` runs, check `node.data('text') === undefined`. If so, fetch via the new message and `node.data('text', fetchedText)`. The cytoscape data store IS the cache — no separate Map needed. All existing reads of `node.data('text')` (in `buildTooltipContent`, bot-context normalisers, Save handler, etc.) keep working unchanged.
3. Sub-200 ms hop on first click of a given node, then nothing on revisit.

**Don't preemptively split.** The current "load it all up front" enables instant double-tap navigation, instant bot-context display, and the simple in-memory mental model. It's load-bearing for the current UX. The day it stops being load-bearing because of network/memory, the above is the cheapest cutover.

**Permanent storage stays in memgraph regardless** — text lives there as `n.text`; the only thing that changes is when the client asks for it.

## How to apply
When user reports "feels slow on phone", first ask whether they mean (a) click-to-text latency (lever 1) or (b) initial load time (lever 2). Different roots, different fixes. See [[chat-panel-state]] for current debounce values.

2. Chrome / Firefox in same tab type → clean output → not a Tone.js bug, not a code bug.

# Socket.IO migration (2026-07-11 → 2026-07-12)

Chat transport moved from raw `ws` npm package to Socket.IO v4.x. Full topic writeup lives at repo-root `websocketdevels.md` (~500 lines) — this memory is the pointer + non-obvious details you'll want on tap in future sessions.

**Why:** iOS Safari suspends background tabs, killing the raw ws connection inside ~30s of screen lock. Users had to full-reload to recover the pair. Socket.IO's `connectionStateRecovery` + our own grace-period purge give seamless recovery inside 60s.

**How to apply:** When touching transport/pair-state code, keep the two-layer model in mind — Socket.IO handles socket-layer recovery (authenticated session token, message replay buffer); *our* server code handles pair-state persistence (sessions Map cleared on disconnect, pairedWith map NOT cleared until 65s purge fires).

## Current state — verified live on commit `8e61991`

- Fresh connect → sessions++, broadcast user_count
- Disconnect (transport close / ping timeout) → schedulePurge(65s), sessions--, broadcast
- `socket.recovered === true` on reconnect within 60s → cancelPurge, restore sessions, pair intact
- Purge fires only if 65s elapse without recovery → unpair buddy, delete Memgraph User node

Multiple recovery cycles verified in single session on iOS device (transport close → recovered → ping timeout → recovered → transport close → recovered), all inside a paired chat with N_1838.

## The single-'msg'-event minimal-diff pattern

We did NOT go to per-type Socket.IO events. Kept the JSON dispatch pattern from raw ws — one event name `'msg'`, `type:` field inside. Translations were mechanical:

| raw ws                                    | Socket.IO                    |
|-------------------------------------------|------------------------------|
| `ws.send(JSON.stringify(x))`              | `ws.emit('msg', x)`          |
| `ws.addEventListener('message', h)`       | `ws.on('msg', h)` (h gets object, no JSON.parse) |
| `ws.removeEventListener('message', h)`    | `ws.off('msg', h)`           |
| `ws.readyState === WebSocket.OPEN`        | `ws.connected`               |
| `ws.close()`                              | `ws.disconnect()`            |
| `ws.userId` (custom prop on ws instance)  | `socket.data.userId`         |

Variable name `ws` kept everywhere on client side (despite being a Socket.IO Socket) — minimal diff.

## Non-obvious gotchas

### G1. Handler must be attached BEFORE first emit (commit 4e5451c)
Under raw ws the browser buffered incoming messages during script parsing, so emitting before attaching the message listener was tolerable. Under Socket.IO, events received by a socket with no listeners are dropped by the client. Boot order in viewer.js's `init()` must be:
```
ws = await connectWS();
ws.on('msg', dispatch);          // FIRST
ws.emit('msg', { type: 'get_user_count' });   // then
```

### G2. Bulk-replace clobbered window.addEventListener('message') (commit 87461b0)
Python one-liner rewrote `.addEventListener('message', h)` → `.on('msg', h)` globally. Caught two `window.addEventListener('message', …)` calls that were DOM postMessage listeners for iframe communication with V_Kolam — not sockets. Symptom: `TypeError: window.on is not a function` as unhandled promise rejection. Fixed by restoring the DOM API at those two call sites (bd_script_response inbound handler + MM1.6 BD_READY listener in loadModuleForNode).

**Rule for future bulk rewrites:** anchor the pattern on the receiver identifier (`\bws\b|\bwsNow\b`) not just the method name. `.addEventListener('message'` also matches iframe/window postMessage, a different transport entirely.

### G3. 65s purge > 60s recovery window on purpose
Socket.IO's `maxDisconnectionDuration` is 60s. Our `schedulePurge` timer is 65s. The 5s buffer lets a recovery arriving at t=59.9s complete and cancel the purge before it fires. Same-value timers would race.

### G4. `skipMiddlewares: true` in connectionStateRecovery config
Means our cookie-parsing middleware doesn't re-run on recovery. We rely on `socket.data.deviceId` being preserved from the original connect. Correct because bd_device_id is 7-day stable, but noted for future: if we ever add per-connect state that MUST be re-computed on recovery, either flip this to false or handle in the `if (socket.recovered)` branch of the connect handler.

### G5. In-flight message during grace period silently drops
If buddy B does `sendToBuddy(B → A)` while A is disconnected-but-not-yet-purged, server's `sessions.get(A)` returns undefined and the emit is skipped. Socket.IO only buffers messages the server actually *attempted to emit* while socket was disconnected — our skip-if-missing pattern short-circuits the buffer. Deferred fix (see websocketdevels.md §9). Not a security issue.

## Client log forwarding

**Why:** iOS Web Inspector requires a Mac cable — inconvenient mid-test. With log forwarding, one terminal shows both server and client streams for iPhone + laptop simultaneously.

## Substitution + em-dash (BUILT 2026-08-13, Option 2 non-destructive)

Full rules documented in [SR_Editor_Rules_v0.1.md](../../../../butterflydreaming_graphviewer1/SR_Editor_Rules_v0.1.md) at BD repo root. Summary:

- **Alignment mode 4 "Substitute {?…}"** is default. Consumes Smith-Waterman ops per matched span:
  - `sub` (Whisper misheard) → `{?source-form}`
  - `del` (source word Whisper missed) → `{?word}` inserted at right position; consecutive dels grouped
  - `ins` (utterance word not in source, aside or hallucination) → `{?— word —}` wrapped **in place** (non-destructive; em-dashes INSIDE the markers so they survive Accept). Consecutive ins ops grouped.
  - Outside any matched span → left untouched (user commentary).
- **Em-dash boundaries** between commentary and aligned quote. If boundary has soft punctuation (.,;:) it's REPLACED with em-dash to avoid `. — ` doubling. Otherwise inserted alongside.
- **Accept button** strips all `{?` and `}` throughout destination. Em-dashes inside ins-wraps become permanent literary asides. Boundary em-dashes also permanent.
- Nothing ever deleted — the "1 % case where user meant the deviation" is safe.

Design principle (user 2026-08-13): user's speech is **conjectured final literature**. Never wrap it, never quote it, never mark it as "the user said". Only signal what needs review: `{?…}` for substitutions, em-dashes for structural boundaries and asides. Round-trip safety comes from the receiver's Accept button stripping only what's ephemeral.

## Prior substitution plan (pre-implementation, kept for context)

Post-hoc B2 correction (design doc §4 B2) will run after Whisper output. For each recognised word:
- If the word is NOT in a small common-words dictionary, AND
- Has a strong phonetic key match to a source-pane word, AND
- Confidence exceeds a threshold

Then substitute the source form — but **wrap the substitution in tentative-suggestion markers** so the user always sees what was substituted:

```
|?spared||         ← was Whisper's "sped", substituted to source "spared"
|?away||           ← was Whisper's "a way", collapsed to source "away"
```

Two markers: opening `|?` and closing `||`. Chosen for:
- Zero conflict with normal text (both are unusual character sequences)
- Purely ASCII — works in plain `<textarea>` without any styling
- Easy to strip with `.replace(/\|\?([^|]+)\|\|/g, '$1')`

An **Accept button** (near Clear / Copy / Undo) strips ALL `|?…||` markers from the destination in one action.

The user retains full manual editing power: delete the whole `|?word||` chunk to revert, or type over any part of it.

**Broader potential:** this "tentative-suggestion markdown" could be reused elsewhere in BD — e.g. when a paired remote user proposes a rewording of the local text, they wrap the change in `|?…||` and the local user's Accept/Reject reads the markers. Same syntax, general "proposed change awaiting approval" semantics.

BD chat cards are currently plain `<textarea>` (confirmed 2026-08-13 — CM6 integration was reverted, see [[project-a40-codemirror6]]) so this ASCII-marker approach is the right fit — no inline styling needed, works anywhere text goes.

## WebGPU + iOS Safari is a known-broken upstream stack (2026-08-13 research)

Not our bug — the transformers.js / ONNX Runtime Web / Safari WebGPU integration has multiple open unfixed tickets for exactly the "silent tab crash after pipeline load" symptom we hit. Relevant threads:

- huggingface/transformers.js#973 "[safari] Unexpected restarts" — suspected root cause: **iOS Safari WebGPU is float16-only** (no float32), multiple pending ONNX Runtime PRs to fix float precision handling. This is likely THE upstream fix eventually.

- transformers.js#1518 "Still crashing using WebGPU" — the "still" is telling; unfixed across releases.

- transformers.js#1298 "Whisper web demo not working on iOS" — Xenova's OWN official demo broken on iOS Safari.

**Policy:** don't re-enable WebGPU on our own initiative. Wait for a transformers.js release note that explicitly claims iOS-Safari-WebGPU-ready (probably tied to ONNX Runtime float16 PRs landing). # View-scoped hint properties (2026-07-23)

## The problem the change fixes

Before: `hint_x`, `hint_y`, `hint_scale` on each edge. Single slot per edge.

DAG edges participate in **at least two** views. A Family→SubFamily edge (say `Nature → Animals`) is a "child edge" in Nature's view *and* a "parent edge" in Animals's view. Writing arrangements from either view stored a hint on that same edge — whoever Wrote last owned the slot, wiping the other view's arrangement.

The user described it as "prodigious crosstalk between the layouts that tends to undo the one you did before". Every SubFamily has 1–4 top-Family parents. Every Cluster has 1–3 SubFamily parents. So most edges were in this cross-owned state.

## The fix

Each edge now carries **view-scoped** properties:

- `hint_x_<parentUuid>`
- `hint_y_<parentUuid>`
- `hint_scale_<parentUuid>`

Where `<parentUuid>` is the UUID part of the "viewing" parent's URL (last `/`-delimited segment of `butterflydreaming.org/n/<uuid>`).

A Nature→Animals edge can now hold:
- `hint_x_89f66c09-4769-4bdb-9f89-c44319e7a3ea` (from Nature's view)
- `hint_x_238cceba-00b3-4389-b88b-f8762e280034` (from Animals's view)
- (plus y and scale variants for each)

Reader picks the property matching the currently-expanded parent's UUID. Different views coexist on the same edge without clobbering.

## Wire format

Client sends each hint as:
```js
{ relId, props: {
    [`hint_x_${parentUuid}`]: 0.527,
    [`hint_y_${parentUuid}`]: -0.301,
    [`hint_scale_${parentUuid}`]: 288.5,
  }
}
```

Server merges via `SET r += h.props` — additive, doesn't disturb other keys (edge weight, legacy hints, hints from other views' UUIDs).

Backward compat: server still handles the old flat shape (`h.hint_x` etc) — dispatched at query-build time by peeking at the first hint's shape. Old clients keep writing bare keys. If we ever revert the client, the server still works.

## Reader fallback

`runLayout` in viewer.js defines closures per invocation:

```js
getHintX     = e => e.data(`hint_x_${parentUuid}`) ?? e.data('hint_x');
getHintY     = e => e.data(`hint_y_${parentUuid}`) ?? e.data('hint_y');
getHintScale = e => e.data(`hint_scale_${parentUuid}`) ?? e.data('hint_scale');
```

If a parent has no URL (defensive — every current node does), the closures collapse to just the bare keys. If a view-scoped key is present, it wins; otherwise fall through to the pre-2026-07-23 bare key. Every edge with hints from before the change still restores.

Used in three places within runLayout: the hint-scan filter, the preset positioning loop (`graphCx + getHintX(e) * renderScale`), and the hybrid unhinted filter.

## The `hint scan` console log now includes the UUID

```
[BD] hint scan: parent=Nature uuid=89f66c09-4769-4bdb-9f89-c44319e7a3ea total=23 hinted=23 mode=preset hint_scale=288.5 formula_scale=489.9
```

If `uuid=(none)`, the parent has no URL — closures collapsed to bare-key fallback. Should only happen for legacy nodes if any exist.

## Gotchas + why they're OK

### G1. Hyphens in property names
Memgraph property keys accept hyphens via `SET r += $props` parameter binding — verified 2026-07-23. Manual Cypher `r.hint_x_898...-...` would trip parser (`-` reads as subtraction), so any ad-hoc queries need `` r.`hint_x_898...-...` `` backtick-quoting. Not a concern for the code path — everything goes through map access.

### G2. Property count grows
An edge shared between N views ends up with 3N+3 hint properties (view-scoped × N plus legacy bare). Not a problem in practice — edges in this DAG have 2 endpoints so N≤2, giving ≤9 hint properties per edge. `bd_tool.js read <name>` shows a longer property list on shared edges; that's the audit trail.

### G3. Refuses Write when parent has no URL
`dev-write` bails with `parent has no URL — cannot save view-scoped hints`. Defensive — every current graph node has a URL after the 2026-07-16 backfill, so this is a bug-catcher, not a user-facing constraint.

## Revert path

Two commits: `f14ed4f` (code) + `298b336` (nav_nodes_text.md flag-reset from prior write). Revert `f14ed4f` alone restores single-slot behaviour. All view-scoped keys stay on edges as inert history — nothing reads them once the code is back. No data loss on revert; no cleanup needed.
