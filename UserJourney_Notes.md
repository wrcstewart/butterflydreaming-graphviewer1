# User journey — notes (2026-11-14)

On 2026-11-14 the author made a run of small changes "in the interests of
helping the user journey". Each of them guides a first-time reader through the
opening of BD: Root → Arriving → Settling → Conversations → a family → its
clusters. All are in `viewer.js`, plus `style.css` and `index.html` where
noted, and each was checked in headless BD before it was committed.

## 1. The Root card's tap hint, removed (`cae2669`)

The Root card ended "Tap once more to see connected nodes." The author:
"not needed". Root's last message already reveals its children by itself (the
`(isRoot || isArriving) && isLast && hasNavDescendants` block in
`advanceOrNavigate`), so the hint asked for a tap that did nothing new.

- **What changed:** `getChunkHint` now returns `''` for Root as well as in
  one-tap mode: `(oneTap || isRoot) ? '' : CHUNK_HINT_NAVIGATE`.
- **What did not change:**
  - Root's "Tap for next message from me." between messages;
  - the hint on other nodes under `?uf=0`, where the extra tap is real.
- The hint is **generated by code, not stored text**, so no database edit was
  involved.

## 2. The route already taken goes quiet (`3490228`)

The author: at Conversations, "there should not be a thick white arrow line to
it — the user has already taken that route so doesn't need reminding. Please
make normal thickness and dotted like Settling."

- **The rule:** `applySeqSignals` gives the class **`route-taken`** to every
  `CONTAINS` edge *into* the centred node.
  - `CONTAINS` is the main-route relation: Root→Arriving, Settling→Conversations,
    Settling Meditation→Conversations, and others.
  - The style matches `edge[?aside]` (Settling's look): dotted, 1px, #6a6a72,
    opacity 0.45, with a small grey arrowhead.
- **It is general, not special to Conversations.**
  - When you are on Arriving, Root→Arriving is dotted too.
  - Leaving a node, the same edge is the way *on* and keeps its bright route
    look.
- **Settling's edge was already dotted, for a different reason.** It carries
  `aside: true` in the database (2026-10-26).

## 3. Journey arrows (`3490228`, `c1ca0e0`, `8dcea92`)

Arrowheads at a hub say which way the usual route runs. One table drives them:

```js
const JOURNEY_ARROWS = {
  Conversations: { away: '*' },
  Music:         { away: ['Drone', 'Fractal', 'Scores'], toward: '*' },
};
```

- **The key** is the centred node's `name`. The neighbours listed are its
  `DESCENDS_FROM` neighbours, also by `name` (not `display_name`, which can
  carry line breaks: "Pattern\nRecognition").
- **`away`:** an arrow from the hub out to these neighbours (`'*'` means all).
- **`toward: '*'`:** every other neighbour gets an arrow pointing in to the hub.
- **`except`:** neighbours left plain. Music once excluded Arts; the author
  then asked for Arts to point in too, so nothing uses `except` now. The
  mechanism stays.
- **Which end gets the head is worked out per edge.** An edge's source and
  target come from the database, and they are not consistent: Music's links to
  Drone, Fractal and Scores are stored running *into* Music, and its five theme
  clusters *out* of it. So there are two classes:
  - **`jh-target`**: the head is at the edge's target;
  - **`jh-source`**: the head is at its source.
- **Head colour.** The `DESCENDS_FROM` line colours are set **inline** by the
  colouring loop (a bypass, which a stylesheet function cannot read back). So
  the loop also records each colour in `data.lineColour`, and the arrowhead
  rules read that.
- **Adding a hub is one line in the table.**

The author's words:
- Conversations: "put an arrow to it and to all the 6 circular nodes so as to
  invite user to move on".
- Music: "Drone, Fractal and Scores with an arrow to them but the other nodes
  having an arrow head terminating at the Music node itself. Indicating the
  most common route is from them towards the Music node."
- Then: "Arts node should be incoming to Music too".

**Known look:** in its cluster view Music's own node is small, so the six
incoming heads bunch together at it.

## 4. Gateways' line, grey not white (`3490228`)

The author asked for the line to Gateways to be "the same thickness as the
others". **Measured, it already was:** all seven lines out of Conversations are
2.5px. Gateways' line resolved to Gateways' own **white**, while the families'
lines are mid-tone colours, so at the same width the white one read as
thicker.

- **The fix:** the `DESCENDS_FROM` colouring loop uses **#8c8c8c** when the
  resolved endpoint is Gateways. That is a grey at about the families'
  luminance (relative luminance ~0.25), so all seven read equally. The width is
  unchanged.
- The author was told this and did not object. Keeping it white and thinner
  instead would be a one-line change.

## 5. Collage is Create-only (`169c3ab`)

On 2026-10-20 the author asked for the Collage button to be hidden in Browse.
It was, but the CSS rule and the `collageModeOk` guard **both** allowed
`player-active` as well. So in Browse, with a module node open, the button came
back and wrote into the card stack: an authoring action offered to a reader,
who cannot save it.

- **The author's question:** "Is there any point in showing the Collage button
  in Browse mode ... it might confuse the user?" Advice: Create only, because
  making is Create, and readers still *play* collages. The author agreed.
- **Now:** `body:not(.edit-active) #collage-btn { display: none; }`, and
  `collageModeOk = () => body has edit-active`. A press in Browse logs
  "Collage is a Create-mode action. Switch to Create first."
- **Both sites must change together.** Each points at the other.

## 6. The retrace reminder at Conversations (`f21621f`)

The author: "a little reminder to appear about 10 seconds after arriving there
... a sentence in the buttons bar to the right of the Local button saying Hint:
Press here to retrace your steps. and before that sentence a little left
pointing arrow."

- **Markup:** `<span id="retrace-hint" hidden>` right after `#back-btn` (the
  Local button) in `#bd-toppanel`, reading "◀ Hint: Press here to retrace your
  steps." It fades in.
- **Style:** sans-serif 12px, #e0e0e4, with the arrow in white. On a narrow
  phone it shrinks and wraps (`flex: 0 1 auto; min-width: 0`) rather than
  pushing the buttons.
- **Logic:** `retraceHintFor(centre)`, called at the top of `applySeqSignals`.
  - **Only a change of centre counts as arriving**, so a re-layout of the same
    view does not restart the ten seconds (`RETRACE_HINT_DELAY_MS`).
  - Leaving Conversations cancels a pending reminder and hides a shown one.
  - It shows only if Local itself is on screen (`.visible`); otherwise it logs
    why not.
- **Retired once Local is pressed** (`retraceHintUsed`, set in Local's click
  handler), for the rest of that page visit. This was my choice, not the
  author's, and the author was told. Showing it on every arrival is a one-line
  change.

## 7. How these were tested

All headless Chrome against the running server (`localhost:8080`), via a
throwaway probe page in the repo root (deleted after each use). The probe page
iframes BD and reads `window.cy`, computed styles and DOM state.

- **Getting to Conversations:** emit `tap` on Root, then Arriving, then
  Settling (twice), then Conversations. Click **Continue** on the
  development-version code dialog and **Not now** on the speech offer as they
  appear, or every later tap is blocked.
- **A hub by link:** `/n/<uuid>` arrives centred on that node. Music is
  `a8c58545-9584-475d-a8cf-746f06f6035f`.
- **What to read for an edge:** `width`, `line-style`, `target-arrow-shape`,
  `source-arrow-shape`, both arrow colours, and `classes()`. A line's colour
  can be an inline bypass, so read it from the rendered style, not the
  stylesheet.
- **What could not be reproduced:** Browse **with** `player-active` did not
  occur on a headless arrival. The Collage CSS was tested by setting that state
  on `<body>` directly.
